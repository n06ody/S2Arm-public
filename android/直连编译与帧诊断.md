# 直连编译与帧诊断

此诊断缺省关闭，仅调试包且 `debug.s2a.debug_env=1`、`debug.s2a.direct_trace=1` 同时满足时，在直连选定后启用。生产包不认开关。以现有运行器的本局随机 `debug.s2a.session_uuid` 绑定证据；没有这个锚、不能与运行器本局 UUID 和 PID 对上时，归属未证。

每约五秒在应用私有 files 目录发布一个 `direct-trace-<pid>-<session>-<段号>.jsonl`，含从 0 开始的连续段号、会话号、UUID、时钟、区间、记录数、累计丢失数，以及覆盖头和全部记录的 SHA-256。完整内容先写 `.partial` 并同步，完整文件发布后才可读取；`.partial`、缺段、校验不符、丢失数非零均不得当作完整证据。强停仅保证已发布段可取，最后已发布段之后的区间未证。目录已存在的同名文件不会覆盖；写入失败日志报红并终止采集。

回放每次成功交上屏记一条帧时刻：相邻帧的差是 CPU 交呈现引擎间隔，不是真正显示时刻、GPU 耗时或扫描时间。现场编译在编译器调用前后记录配对事件：程序内容身份 SHA-256、阶段位（VS=1、FS=2、GS=4、CS=32）、是否提交线程、是否命中预热、成功与否；每次实际调用均记录，含失败和重试。成功预热或其他缓存直接返回不调用编译器，因此无现场编译事件；现场事件的 `warm_hit` 为 0。只用 `CLOCK_MONOTONIC` 起止算编译耗时和帧间隔，`boot_us` 在安卓是 `CLOCK_BOOTTIME`，用于对齐运行器采样窗口，不能跨时钟相减。编译跨段未结束时保留 begin；若直到最后完整段仍未结束，则标 in-flight，不得当作零次或零耗时。

将本局连续段原样取回并另行核对源/目标字节与 SHA-256、PID、UUID 后，运行 `python3 android/direct_diag_reader.py <按文件名选出的所有本局段>`。输出 JSON 含完整覆盖区间、逐帧时间及间隔、配对编译起止与纳秒耗时、未结束编译。只分析覆盖在区间内的场景；最后一段外的路线或持续中的编译没有完成证据。采集、取回及设备操作由 QA 执行。

## 场景时间线（v2，诊断包）

`direct_trace` 现在也记录新回放层实际驱动建管线、预编库查询与贴图上传。每条事件仍使用分段、丢失计数和 SHA-256 合同；v1 消费方应拒绝 v2，不得静默忽略新事件。分段缓冲每 5 秒最多 16384 条记录，满了丢失数非零，整段不能作完整账。诊断会产生额外 CPU / IO，不能把开诊断局当无开销性能基线。

- `pipeline`：`kind` 1 客机图形、2 客机计算、3 清屏、4 深度搬运、5 缩放、6 BC 解码、7 图形在途等待、8 计算在途等待；`warm=1` 表示记录线程是后台预热。1–6 的时间是 `vkCreate*Pipelines` 调用墙钟，7–8 是等待另一个线程建管线的墙钟（不计作新建）；不等于 GPU 完工，也不全是客机首遇。`feedback=0` 未知（扩展没启用或反馈无 VALID），1 有效但没有报告应用缓存命中，2 有效且报告命中。1 不证明驱动缓存未命中；创建失败也不计入命中率。应用实例按 Vulkan 1.1 建，只有设备明确列出且诊断门打开才启用 `VK_EXT_pipeline_creation_feedback`；BC 解码使用空应用缓存，反馈记未知。设备不支持时照实报未知，不关扩展或校验层。
- `pack_lookup`：按程序内容身份和前台 / 预热分类。原因：1 无 revision 根、2 图形阶段不是 VS+FS、3 图形状态不符、4 调试开关关闭库、5 此身份之前建对象失败、6 无库容器、7 容器拒收、8 条目缺失、9 条目拒收、10 取到候选字节、11 候选不能建程序。10 后可能跟 11，不能把两条当两支程序；统计唯一程序按身份去重。只有其他离线结果和私有缓存没取到才查 LibPack：此前已命中的程序不产生查包事件，包覆盖应记未观察，不能当命中或缺失。条目拒收只有大类，具体损坏原因仍看原始日志，不由诊断猜。
- `texture_upload`：`kind` 1 存储首次初始化，2 CPU 贴图首传，3 CPU 贴图重传，4 客机缓冲到贴图的区域拷贝，5 存储初始化填零，6 内部默认零贴图；`method` 0 未完成、1 整次操作 / 指定区域、2 脏行局部。`bytes` 是传给后端的源字节总数，可能包含来宾指定的行距；失败时为已尝试的部分。`reason` 位：1 首次、2 前次失败待重试、4 查询时无跟踪区间、8 查询时全局跟踪不可靠、16 脏查询返回真。4 / 8 是保守判脏证据，16 不必然证明 CPU 真写过；标志是在调用前采样。耗时是 CPU 准备、转排和录命令的墙钟，不是 GPU 执行完成或显示完成。只覆盖回放内 `nvn_gpu_tex_upload` 的这些调用点，不能推断所有纹理 IO。

QA 先测热局：同包同设备同锚，第一局正常收尾并核日志确有程序 / 管线清单与驱动缓存写出，第二局不清缓存，核版本、编译闭包、目录与读入、拒因及实际前台现编/现建。固定一个游戏内可操控 3D 场景，记录切场景输入时刻与外部视频判定物体完整时刻，双方须与本局 `CLOCK_BOOTTIME` 对齐并保留误差；不能用 CPU present 自动推断画面已经完整。先做至少三局热局，另按同样流程做至少三对冷→热（冷局只清该游戏 `direct-cache/nvn-vk`；热局不清），记录包 SHA、场景路线、充电与热态。完整画面锚后继续运行超过一个分段周期，确保场景窗口落在已发布的连续段内；取回原始段逐项核字节、哈希、PID、UUID、序号、丢失数与窗口。缺段、未完成事件、没有视觉锚或时钟对不齐均列未证。

```sh
python3 android/scene_timeline.py --pid <本局PID> --uuid <本局UUID> --start-us <切场景BOOTTIME微秒> --complete-us <画面完整BOOTTIME微秒> <本局连续段...>
```

输出每个相交事件和汇总；跨窗口事件贡献其完整耗时与字节，不可把相互重叠的墙钟直接相加当卡顿归因。帧数统计只包括两端均位于该窗口的相邻成功 present；`p99` 用最近秩，空区间为 `null`。场景是否完整是外部输入，分析器不验证画面，也不把本机缓存文件大小当命中率。

## 纯工作量类的小效应用同局交替，不用分局对照（11-12）

量「开一个开关省不省 GPU / CPU 时间」时，效应在 1 ms 级就不要分局比：机身热起来后 GPU 降频，同一配置连跑两局，每帧 GPU 中位能差 4 ms、整机差 1 W 以上（11-12 实测：同包同开关两局 13.19 / 17.32 ms），局间波动把效应盖掉。

做法：被测开关做成按出图次数分段交替（偶数段关、奇数段开，例如每 120 次出图换一次），一局里采 200 秒左右，拿相邻的「关、开」两段凑一对：

- 每段丢掉首尾各 15 帧（切换瞬间与在途提交），取段内每帧 GPU 时间的中位数；
- 报成对差的中位数、均值，以及「开更低」的对数 / 总对数；
- 同时报两臂每帧绘制笔数的中位数：差得多说明自动玩家路线让场景对不上，这局不算；
- `frames.tsv` 第 n 行的 `gpu_us` 是第 n − 1 帧的，分段时按「帧号 − 1」算段号。

这样两臂在同一局、同一热状态、相邻场景里，局间波动成对抵消。11-12 一例：38 对，成对差中位 −0.65 ms（−4.1%），27 / 38 对开更低；而同一改动分局跑四局分不出方向。

整机功率、帧率这类大效应（差 1 W、差 10 帧以上）仍可分局比，但要写明每局的热状态，电量 100% 且不在充电（账本「充满」）才进定量。交替开关属于被测改动本身，不算重探针；带它的局写明「同局交替」。

## 功率、调度、频率、刷新节拍类改动：热机稳态整局对照（11-12）

改动只要会影响功率、线程调度（调度档、实时声明、亲和）、核心频率或刷新节拍，而不只是改每帧工作量，入车前就按整局量，不用同局交替：

- 同机、同场景，先把机器跑热到稳态（连跑一两局，直到帧率与整机功率不再逐窗口变化），再开始计数；
- 开、关各至少两局，交错排（关、开、关、开），每局写明热状态与供电；
- 判据是帧率和整机功率，同时报进程 CPU 功率、性能核用量；有动态分辨率的游戏再报主遍分辨率。

为什么不用同局交替：手机稳态整机功率是定的，CPU 多花的功率由系统从 GPU 上扣回去，这个过程有几十秒的时间常数，比交替的段长得多，交替量出来的方向可以是反的。11-12 一例：提交线程实时声明用同局交替量出帧率 +12% / +20% 后合入；当晚热机整局对照，开 30–39 帧、进程 CPU 0.57–0.76 W，关 42–47 帧、0.34–0.45 W，随即撤回。

有动态分辨率的游戏还有一层：省下的 GPU 时间会被游戏拿去升分辨率，每帧 GPU 时间看不出变化。量这类游戏时，尺子是帧率加主遍分辨率（`DM_NVN_GPUPROF` 取 100 帧看主遍尺寸），不单看 GPU 时间。

### 安卓回写暂存的会话内自动试测

调试包启动前设 `debug.s2a.nvk_land_readback=auto` 即在本次后端会话的成功呈现上自测。0 为缺省关，1 强制尝试暂存。各臂使用相同的读档、入场、前推与尾窗流程。

每个观测窗至少 5 秒、50 个完整成功呈现间隔，并须有新增绘制和候选回写字节。样本稀疏或没有相关工作的窗口丢弃；即使黑屏快速呈现，仅凭帧数也不会收窗。系统没有画面识别，有绘制且有候选回写的载入画面仍可能合格。前后台、热档、现编累计或呈现目标变化时重新取同条件窗口。在途旧段完成后才计新窗。试测期间暂存开启窗变稀疏时先回关，经有效的恢复窗后再试同一档；恢复窗不计入配对。

先用六个 R0 窗形成三组不重叠 A/A，取各项配对差的最近秩 p95。再用 R0、R1、R1、R0 配对，首次切 R1 另需一个预热窗。w0–w5 校准，w6/w8、w10/w9 是两组关/开对，w7 预热。每个有效 R1 窗要求完成暂存回写。两对均须提升 FPS 超过 max(5%, A/A 相对 FPS 差)，并通过尾窗、呈现压力和工作量对照。锁开需要 11 个合格窗。连续 11 个呈现和绘制均足量、候选回写字节始终无增长的窗口会锁关（no_completed_staging），这些窗口不计入配对。按真实路线采，提前退出按样本不足记录。

`回写自动决策` 的 `phase=lock` 记录实际锁档，`phase=exit` 在正常退出时复述该决定；尚未完成则记录 `mode=0 reason=insufficient_samples`。两行的 `decision_boottime_ns` 是同一锁档时刻（Android CLOCK_BOOTTIME 纳秒；0 表示不可用）。`qualified_windows` 为当前可比较组已收窗口数，`invalid` 为丢弃计数，w0 至 w10 的首列为各窗有效间隔数。计分应以本进程的 host 日志和出生标识对齐；进程被强杀可能没有退出行。

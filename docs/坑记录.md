# 坑记录

从这里开始记录，每条写现象、根因、改法。

## 错误摘要把同一原包按内容记录重复计数（issue #128）

**现象**：同一原包在 catalog 中分别提供 base、update 记录时，错误摘要保留两条包明细，也把原包合计算了两次。

**根因**：`report.game_lines()` 直接累加所有 `packages[].size`，没有按 catalog 的 `sha256` 来源身份去重。

**读数（期望 → 真结果）**：Mac arm64、基线 `c36447f97`，临时 catalog 中两条共享来源、各记 4096 字节的包记录；原包合计应为 4.00 KB → 修前 8.00 KB、修后 4.00 KB，两条包明细保留。摘要测试 10/10 通过；换回基线实现后 4 处断言重新失败。同身份不同路径、不同身份同路径、无路径、缺少或空身份同测。

**做法**：只对非空 `sha256` 的来源去重，缺少身份的旧记录仍分别累加；使用 catalog 已存大小，不读取原包文件。
## 打包纹理的附件与 image 写入要参与局部重上传保护（11-10）

**现象**：256×256 RGBA8 打包纹理先由真实 GPU 整张写红，CPU 随后只把 `(0,0)` 写绿；另一宿主页的 `(255,255)` 却恢复成初始蓝色。

**根因**：附件绘制与 image store 只记全局 GPU 旧字节账，未维护已有 `NvPkg.pgpu`。后续 CPU 局部改页时，已有打包纹理走整张重上传，从旧 guest 字节覆盖未被 CPU 修改的 GPU 内容；首次转成打包纹理的 `carry_gpu` 无法覆盖这个路径。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0，基线 `af2bd1481`，生产 draw 与 rw-image dispatch 各先独立读回确认两角为红色，再验证 CPU 改绿及另一页保红。Metal 3 / 4 各 12 项应全绿 → 修前各 4 红（正常采样和独立 GPU 读回的远端均错回蓝）、修后共 24/24 绿；回退同一写入标记调用后两路各 4 项重新变红。

**做法**：子资源写入入口同时维护全局旧字节账与打包纹理的 GPU 页记录，复用已有部分重上传路径。回归只验证不同宿主页，未扩展同一页内的细粒度 CPU/GPU 合并范围；这些读数不代替游戏画面验收。

**缩小存储边界**：局部重传矩形使用游戏坐标，不能贴到内部分辨率缩小后的存储。Mac M5 Pro / macOS 27.0，`e3d9ed78f` 的 256×192 打包颜色目标缩到 128×96 后，CPU 改一个像素：期望重建 256×192 → Metal 3 / 4 各仍为 128×96（各 1 红）。局部重传增加宽高不小于游戏尺寸的条件后，两路各 4/4 绿：重建原尺寸、GPU 读回更新像素为绿及远端 guest 原字节为蓝、下一渲染遍再缩到 128×96；仅回退尺寸守卫后两路各 1 红，恢复后两路各 4/4 绿。缩小存储沿用整张上传，宽高均足够的存储保留局部上传。
## NVN 结束上一遍不能隔离下一笔的附件自采样（#296）

**现象**：惊奇 1.2.1 的 iPhone 15 Pro Max / iOS 18.6 诊断包（宿主 `c4adca3d0`）记录 Metal 3 直连，每 300 帧常见 600 笔结束遍后采样、快照和片上读取均为 0；报告者在开头移动、跳跃时见闪烁。该日志只能定位反馈路径，不能单独证明闪烁根因。

**根因**：`fb_prepare()` 默认允许写入采样槽的绘制直接读取原纹理。附件未脏时不做隔离，已脏时只结束上一遍；新遍仍会同时采样并写同一资源。只验证特定 GPU 恰好画对像素，会漏掉这个未定义读写路径。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0（26A428）、基线 `92f980f04`，真实生产绘制与参数编码，Metal 3 / 4 各测默认 7 项和强制快照 5 项。自写槽在未脏 / 已脏两例中应绑定独立采样资源 → 修前两路各 2 项失败（采样与附件资源 ID 同为 `0x1`），修后共 24/24 项通过；原始 GPU 像素检查在修前也通过。候选设置 `DM_NVN_FB_SELFREAD=1` 恢复旧路径后，两路均重新出现这 2 项失败。另有 mip 钉级视图回归两路各 6/6 通过。

**做法**：保留已证明可用的片上读取，自写槽其余情况默认采样已有快照；不写采样槽的绘制保留无需拷贝的路径。本次未完成游戏开场和 iPhone 同包 A/B，不把 GPU 单测当作 issue 画面验收；新增快照的真机帧时与能耗影响待测。

## GL 直连预检与翻译器的工具选择不一致（issue #269）

**现象**：`GLSLANG` 指向可执行工具、PATH 没有 `glslangValidator` 时，纯 GL 提前报缺工具，混合 GL 跳过离线库；这不证明 issue 报告者的失败属于同一原因。

**根因**：`direct_lib.sh` 检查 PATH 上固定名称，`gl_shaders.py` 则使用 `GLSLANG`（仅未设置时回退固定名称）。

**读数（期望 → 真结果）**：Linux 容器、基线 `31bfb8d`，合成工具和隔离 PATH，纯 GL 入口与混合 GL 分支各测 9 种情况，共 18 项；空格路径的显式工具应被调用 → 修前两分支均未调用、修后均调用；回退生产检查后两分支再次未调用。未设置变量时的 PATH 回退、无效或空变量和缺 `spirv-cross` 同测。未跑真实 Windows、Mac 出包或游戏复测。

**做法**：两处分支按翻译器相同的变量选择检查可执行文件；保留缺工具时各自的失败方式。
## Mac 手柄输入停在 120Hz 定时器网格上

**现象**：Mac 上蓝牙 DualShock 4 的按键 / 摇杆从系统事件到前端发布均值 4.21ms、中位 4.29ms、P99 8.36ms、最大 8.92ms，分布落在 1/120 秒（8.33ms）的网格上；同机键盘走 keyDown 事件路径，中位 0.56ms。

**根因**：`macos/front_mac.m` 只在 1/120 秒的 NSTimer 里调用 `poll_input()` → `sample_input()`，`GCExtendedGamepad` 没有接 `valueChangedHandler`；iOS 侧已用事件回调（`ios/controller.m`）。

**实验数据（期望 → 真结果）**：Apple Silicon Mac（Mac17,3，macOS 26.7.1）、蓝牙 DualShock 4、游戏《怒首领蜂大往生 临回转生》59.96 fps。手柄前端 420 条状态变化：均值 4.21ms / 中位 4.29ms / P99 8.36ms / 最大 8.92ms → 改为 `handlerQueue = main` + `valueChangedHandler` 后回调直接 `sample_input()`，不再有定时器量化；单测验证回调发布整份当前状态，长按跨回调和 120Hz 回退采样仍保持。

**做法**：`install_pad_handler()` 给每个 `GCExtendedGamepad` 装 `valueChangedHandler`，回调里 `sample_input()`；120Hz 定时器保留给键盘 / 鼠标粘键核对并补装新连接的手柄。

## 覆盖更新中断后重试删除唯一旧版备份

**现象**：安装目录已改名为 `.s2arm-old`、新版还没改名到安装位置时中断，再次执行 `apply()` 会删除旧版备份，随后因安装目录不存在而失败。

**根因**：更新入口无条件清掉已有备份，再调用要求安装目录存在的 `swap()`，没有恢复两次改名之间的中断状态。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`；用合成目录构造第一次改名后的落盘状态。重试成功安装新版 → 改前失败且旧版消失、改后成功；新版暂存目录丢失时保留并重启旧版 → 改前旧版消失、改后恢复旧版；恢复改名被拒时原备份保留 → 改前消失、改后保留。`ApplyTests`、`RunnerTests`、`Ed25519Tests`、`VersionTests` 共 15 项通过。临时副本换回基线 `updater.py` 后，两项点名回归重新失败。

**做法**：安装目录缺失而旧版备份存在时先恢复旧版，再走正常替换。未执行真实安装包更新、断电或 Windows 文件占用验收；该验证仅覆盖两次改名之间的中断状态。

## 清理中间产物时沿链接删除存档目标

**现象**：`iPhone/<程序号>/intermediate` 是指向同库 `saves/<程序号>` 的目录链接时，`prune_build()` 删除存档目标，链接本身却留下。

**根因**：`library._rm()` 先经 `contained()` 解析链接，再检查 `is_symlink()`；目标仍在游戏库内就通过了包含检查。父目录是链接时也会删除它指向的文件。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`，均为临时目录与合成字节。自动清理后存档保留 → 改前文件消失、改后内容原样保留；显式清理、库外目标、文件链接和悬空链接同测。`test_cleanup_links`、`test_free_space`、`test_saves` 共 63 项：62 项通过、1 项 Windows junction 用例因宿主不符跳过。临时副本换回基线 `library.py` 后，两项点名回归重新失败。

**做法**：先核对未解析的路径是否属于清理根，拒绝经过父目录链接；叶子链接只删除链接本身，Windows junction 使用 `rmdir`。未做 Windows 真机验证，也不据此宣称能消除并发路径替换的所有竞态。

## 发版 Mac App 出包失败：shader_extract_failed（issue #8）

**现象**：  
发版 Mac App（如 v0.1.0），游戏 RomFS 要解码器（Oodle LZ5）或运行时 GLSLC 时，出包报 `shader_extract_failed`，阶段停在「分析画面」。

**根因**：  
- `pack/stage_extract.sh:63` 调 `tools/host_build.sh` 现场 make 编 Mac 宿主（含 C#，S2A_CS=1）
- 发版 App 只带 Runtime（`pack/jobs/core.py:500` 设 `DOTNET_ROOT=Runtime/dotnet`），无 SDK
- make 的某步调 `dotnet --version`，Runtime-only dotnet 报「No .NET SDKs were found」退非 0
- 失败被 `stage_extract.sh:63` 归因：「【红】t<游戏 ID> 编译 Mac 宿主失败（The command could not be loaded...）」
- 上层按阶段 `sh_extract` 映射错误码 `shader_extract_failed`

**实验数据**：  
- 设备：Mac（发版 App v0.1.0，S2ABuildID=7aff9afa-86be9c95）
- 数据目录：<本机复现用的临时数据目录>
- 游戏：010021C000B6A000 以撒重生+ v1.7（中文忏悔本，含 Oodle LZ5 → decoder_need 为真 → S2A_CS=1）
- 期望：ipa completed
- 真结果：rc=1，analyze 2/10（26 秒），错误码 `shader_extract_failed`
- 日志证据：
  - `Runtime/dotnet/dotnet --version` 输出「No .NET SDKs were found」
  - `refresh.log` 第 8 行「【红】t010021c000b6a000 编译 Mac 宿主失败（The command could not be loaded...）」
- 负对照：暗黑3（不需解码器）未复现，task completed 346 秒

**做法**（提交 45d5ffe，分支 fix/packaged-mac-host）：  
1. **打包时已放宿主**：`launchers/macos/bundle_engine.py:179` 已有 `shutil.copytree(host, destination / "Binaries/S2ArmGame.app")`，打包时把编好的宿主（S2A_CS=1，含 C#）放进引擎 Binaries/ 目录
2. **检测并设环境变量**：`pack/jobs/core.py` 的 `Context.env` 方法，在发版环境（runtimeSchema 3/4）中：
   ```python
   from embedded import artifact
   try:
       bundled_host = artifact(self, "S2ArmGame.app")
       if bundled_host and (bundled_host / "Contents/MacOS/s2arm-host").is_file() and (bundled_host / "Contents/MacOS/libs2a_vaguard.dylib").is_file():
           env["S2A_BUNDLED_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
           env["DM_GLSLC_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
   except Exception:
       pass   # 源码树开发：没有内置宿主
   ```
3. **跳过现场编译**：`pack/stage_extract.sh:51-64` 在需要宿主时，检测 `S2A_BUNDLED_HOST`：
   - 如果设置且文件存在 → 输出「[s2a] 使用发版 App 内置 Mac 宿主：$S2A_BUNDLED_HOST」，跳过 `host_build.sh`
   - 否则 → 按原逻辑现场编译（源码树开发构建）
4. **单测覆盖**：`tests/stage_extract_test.sh` 添加用例「有内置宿主 → 不编宿主、跳过 host_build」

**射程**：  
- ✅ 所有发版 Mac App，游戏需要解码器（Oodle LZ5）或运行时 GLSLC
- ✅ 调用链：oneclick → refresh → stage_extract → extract.sh / glslc_offline.py（DM_GLSLC_HOST 环境变量传递）
- ✅ 源码树开发构建不变（runtimeSchema != 3/4 或 artifact 返回 None 时走原路径）
- ✅ Windows 不受影响（pack/orch/oneclick_win.py，不走 Mac stage_extract）
- ⚠️ 边界：如果打包流程被修改，未把宿主放进 Binaries/，会退回现场编译（因 artifact 返回 None，与源码树开发相同）

**验证**：  
- 单测：`bash tests/stage_extract_test.sh` 全通（23 个 Python unittest + 40+ 个 shell 断言）
- 现有 App：`/Applications/S2Arm.app/Contents/Resources/Engine/Binaries/S2ArmGame.app/` 存在，包含 s2arm-host (106M，含 C#) 和 libs2a_vaguard.dylib (67K)
- 完整打包 + 游戏测试未执行（耗时 15-30 分钟，当前负载 10+）

## 命令行出完包，Mac 前端认不到（装机 / 推资源包报 container_stale）

**现象**：用 `pack/oneclick/oneclick.sh` 命令行出好的 IPA 与资源包都在 `<游戏库>/iPhone/<程序号>/` 下，Mac 前端却说这款没有 iPhone 版；点「装到 iPhone」或推资源包报 `container_stale`。

**根因**：启动器判「这款的产物是不是按本壳出的」看 `<输出>/shell.id`（`pack/jobs/ipa.py` 的 `SHELL_STAMP`，`ipa.current_root()` 只有它对得上当前壳编号才认这份产物）。这份戳只有**启动器自己的打包任务**会写，命令行一键出包（`oneclick.sh` → `ipa.sh` → `ipa_tail.py`）不写，于是产物齐全但前端判「没出过」。

**改法**：`ipa.sh` 出包成功时把壳编号（`<壳目录>/manifest.json` 的 `details.shellId`）写进产物根 `.shell_id` 并随 `root_commit` 提交；`oneclick.sh` 出包成功后把它转交成 `<输出>/shell.id`（与启动器写同一份、同一口径）。

**读数**（期望 → 真结果）：命令行重出这款后 `<输出>/shell.id` → 期望 `e2c369640047cade`，真结果 `e2c369640047cade`；用引擎自己的 `install.latest_ipa()` / `ipa.current_root()` 复核 → 期望返回 IPA 与现行产物根，真结果都返回了（改前 `current_root` 返回 None）。
## 出包停在「出包 2/5」、错误码只有 package_failed「原因没认出来」

**现象**：iPhone 出包到 `出包 2/5` 后工具退出，错误摘要写「Packaging incomplete / We couldn't recognize the cause」（9.78 GB 的 PERSONA4 The GOLDEN，0.1.0，iOS 目标 iPhone 17 Pro）。`pack/ipa.sh` 的 `PN=5` 是 ①组装 ②签名 ③打 ipa ④资源包 ⑤资源包核对；进度只到 2，说明停在 ③「打 ipa」（`pack/ipa_tail.py` 的 `write_ipa` 步）——其余步要么有自己的日志（build.log / sign.log / pack.log / verify.log），要么在 `pack/jobs/ipa.py` 的 `PACKAGE_FAILURE_PREFIXES` 里能映射。

**根因**：③ 这一步有两处把原因丢掉。一是 `ipa_tail.assemble` 调 `step()` 时没给日志，输出落进 `$W/pkg/tail.out`，而 `ipa.sh` 失败时只把 `build.log` 拷进 `S2A_ROOTS/.failed/`、随后 `root_abort` 删掉整个临时产物根，于是真正的原因（体积账 / errno / zipfile 异常）既没进红行也没进摘要；`PACKAGE_FAILURE_PREFIXES` 也没有「打 ipa」这一项，归因只能落到 `package_failed`。二是同一类「原因看不见」的口子：`app_bundle.write_ipa` 按设计不写 zip64（侧载工具读不了），而 32 位上限只有「单文件」一道闸，条目数 / 整份字节超了由 `zipfile` 在写条目或收尾时抛 `LargeZipFile`；它不是 `OSError`，`main()` 的 `except (OSError, ValueError, RuntimeError)` 也接不住，于是变成裸 traceback，父进程只拿到退出码。**这单具体是撞了哪条上限、还是别的 errno，以修复后红行里的原文为准**（IPA 不一定到 2 GiB，先不认定）。

**改法**：③ 有独立日志 `pkg/archive.log`，失败时把最后一行（红行优先）写进红行与错误摘要，`ipa.sh` 失败时也把这份日志留到 `S2A_ROOTS/.failed/`；`write_ipa` 归档前先算体积账（条目数 / 单文件上限能提前判死，整份取决于压缩后大小），收尾的 `LargeZipFile` 转成带体积账的 `BundleError`，`main()` 再兜一层，任何一条路都不落裸 traceback。

**读数**（期望 → 真结果）：归因 `打 ipa 失败（OSError: [Errno 28] No space left on device）` → 期望 `disk_full`，改前 `package_failed`、改后 `disk_full`（`pack/jobs/errors.classify_failure`，合成输入）；`tests/app_bundle_test.py` 新增三条体积账用例 → 改前 2 条 ERROR、改后全绿（34 条，skip 2）；`tests/ipa_tail_test.py` 新增 `archive_reason` 用例 → 改前 AttributeError、改后全绿（7 条）。
## 帧率上限非整除档：生产端交换间隔下限不能四舍五入

**现象**：通用层 `FramePacingPolicy.SwapIntervalFloor` 原来是 `round(vsync / 上限)`，只认 0/30/60/120 时都整除，结果对。放开到任意档后，上限 40 得 `round(1.5) = 2`，也就是生产端每 2 拍出一帧（30 帧），比用户给的上限 40 还慢。

**根因**：交换间隔 k 在 60 Hz 节拍下给 60/k 帧，要「不慢于上限」应取满足 60/k ≥ 上限 的最大 k，即 `floor(vsync / 上限)`（至少 1）。四舍五入在 1.5 这类半值上往上取，就落到了更慢的一档。

**读数**（期望 → 真结果）：`tests/frame_pacing`「40 FPS floor is 1」改前（round）expected 1, got 2，改后（floor）通过；30 / 60 / 120 的下限两种算法同为 2 / 1 / 1，原有断言不变。

**做法**：下限按 `floor` 取，并用非整除的档（40、24）做断言。上限本身仍由呈现端 `MinimumPresentationInterval` 的 1/上限 保证。

## Windows 玩家出 CRI 压缩的游戏：抽取报 WinError 2（issue #95）

**现象**：PERSONA4 The GOLDEN，v0.1.3，Windows 11，「抽取 + 直连库」阶段失败，`direct_lib.log` 只有 `concurrent/futures/_base.py line 401` 和 `FileNotFoundError: [WinError 2]`，后面不带路径。

**实验数据（期望 → 真结果）**：Mac arm64，手机上抓的 P4G 片头 1033 个 NVDEC 作业（movie 37）喂托管解码器，比显示帧 Y 平面 FNV-1a 与 libvpx 1.17.0 直接解 IVF 的结果：修前 → 期望全同，真结果 3/838 相同（不同的从第一帧开滤波的作业起）；main 未带 #86 → 同样 3/838；修后 → 838/838 相同。手机上 #86 构建抓到的 C# 输出与 Mac 重放逐作业相同（1033/1033），不是线程竞争。`tests/vp9_loop_filter_init`：8 档锐度 × 64 级 × 16 字节与 libvpx 公式一致（24576 项）；负对照：删掉 `Decoder.Decode` 里的调用 → 接线检查报红；清空 `hev_thr` 填充 → 6144 项报红。

**做法**：`LoopFilter.LoopFilterInit` 按 libvpx 填阈值，`Decoder.Decode` 设好滤波字段后、`LoopFilterFrameInit` 之前每帧调一次（每帧 64 级 × 16 字节，开销可忽略）。走整段码流的 `DecodeFrame` 路径（S2Arm 不用）没改。

## 文件后备下大块 F_PUNCHHOLE / 大块重映射会拖住整机（11-09，#258）

**现象**：时之笛 S2 在 16 GB M1 Pro（客体内存文件后备自动开）上每约 30 秒整帧停 1–2 秒；`sample` 显示游戏线程在 `UnmapPhysicalMemory` 里逐 16 KB 宿主页 `F_PUNCHHOLE` + 重映射（`svc_mem.c` pages_release → `vawin.c` s2a_guest_zero），全程持 `g_mu`，音频渲染线程等同一把锁。

**第一版修法踩的坑**：把连续页攒成一段、一次打洞 + 一次重映射。微基准很好（同机 256 MB：1083 → 14.5 ms），但真机上开机就冻 11–65 s（所有线程空等、CoreAudio 回调断）、进场景约 1 分钟 Metal 报 `kIOGPUCommandBufferCallbackErrorHang`（4/4 局）。同一构建关文件后备（`S2A_GUEST_FILE=0`）开机、读档、挂机 260 s 全干净；诊断记账 3536 次释放、0 次落在渲染器在用的零拷贝池里，挂死前 30 s 没有任何释放。结论：不是释放段撞上 GPU 在用的缓冲，而是大块 `F_PUNCHHOLE` / 大块 `MAP_SHARED` 原偏移重映射本身让内核拖住整机。微基准只量了系统调用本身，量不出这种拖到后面才爆的代价。

**第二版也踩坑**：锁内只 `mprotect` 成不可访问并记「待打洞」，打洞交给后台线程按原来的 16 KB 粒度逐块做、不再重映射（分支 claude/project-thread-xxrjo1 @ abd69879）。单测、gate、微基准（256 MB 解除持锁 1093 → 25 ms）都好，真机进场景约 34 s 仍报同一个 GPU 挂死，两次整机冻结时后台打洞线程都是空闲的；关文件后备同样干净。两版修法唯一的共同点是 `UnmapPhysicalMemory` 从约 1 s 变成约 25 ms 返回。

**时序实验定位**：在第二版上让解除线程每次 ≥1 MB 解除后停 1 s（锁内、锁外各一组）：6 分钟都不挂，30 s 周期回来；不停：进场景 1 s 后画面停 6 分钟，`sample` 里后台打洞线程一直在 `fcntl(F_PUNCHHOLE)`、Metal 提交线程同时卡在 `IOGPUCommandQueueSubmitCommandBuffers`。即：游戏渲染期间对后备文件打洞，GPU 提交路径就被卡住；原版不挂只因为那 1 s 卡顿本身让 GPU 空闲、打洞做完才有新的 GPU 活。游戏也从不把释放过的地址再映射回来（0–1 次重叠），地址复用那条假设排除。

**第三版（现行）**：文件窗口里释放的页只 `mprotect` 成不可访问并记「待打洞」，根本不打洞、不起线程；游戏映射回来时就地清零。真机 400 s 无挂死、无 30 s 周期；6 分钟释放 1.19 GB 从未打洞，物理脚印稳定在 2.9 GB（脏页留在页缓存，内存紧时由内核按文件后备原设计换出）。`S2A_PUNCH_DEFER=0` 回原路径做负对照；后台线程那版（会挂 GPU）按评审意见删掉，不留半成品。页重新放出来的路径都要处理：0x2C、SetHeapSize 增长、栈区 MapMemory 拷贝路径（先清零再拷）、对齐路径（vm_remap 盖掉，只撤销标记）——评审在 UnmapMemory → MapMemory 这条上抓到过漏撤销标记。

**教训**：改文件后备的还页路径时，微基准之外必须进游戏跑：看开机有没有长冻结、进场景后 GPU 有没有报错，而不只看卡顿有没有消失；同一构建加 `S2A_GUEST_FILE=0` 做负对照。时序实验与结论见 #258。

## 装 NRO 补绑导入时，槽已被游戏设成只读

**现象**：玩家 iPhone 17 Pro Max（iOS 27.3）上 01001BA027DD8000 起局约 0.4 秒闪退，连崩 3 局，SIGBUS 都在 `s2a_nro_map`，地址都是 main+0xb958d0；同一个多款容器包里的另一款正常。

## Metal 3 下计算派发的绑定会把共享编码器换掉

**现象**：时之笛 S2 在 macOS 15（#261，玩家 M4 Pro）上开场过场后 SIGSEGV，崩在 AGX ComputeContext `setBuffer`，栈 `m3_table_apply ← enc_c_dispatch ← dispatch`，崩前一行是「texture upgraded to allow format views」。Mac 上 `NXGAL_BE=mtl3` 稳定复现（第 10614 帧）。

**根因**：`dispatch` 先取共享计算编码器 `ce = dispatch_enc()`，再 `encode_args` 绑参数。绑图像 / 贴图视图要格式视图用途时会升级贴图（`tex_upgrade`），升级的拷贝走 `blit()`。Metal 3 拷贝要拷贝编码器，`blit_open_k` 会结束共享计算编码器 `g_blit`，本地 `ce` 成了已结束的编码器，接着派发就崩在驱动里。Metal 4 拷贝和派发同一个编码器，不换，所以只在 Metal 3（macOS 15 / iOS 18）出。绘制路径 11-02 已修过同一个坑（`draw` 绑定后检测 `g_enc != en` 重画）。

## 已装的内置引擎副本被改过，出包一直报「准备产物缺失或大小不符」

## 首写表的「槽号」其实是着色器内存储缓冲序号

**现象**：Splatoon Raiders（#41）对话后卡到一秒一帧。实局卡顿场景里每帧绘制笔数不变（约 1370 笔），GPU 时间却一路涨：91 → 565 ms（约 180 帧内）。

**根因**：一笔间接绘制（实例数由剔除计算着色器 `029d9c3ec1fcb39f` 用原子加写出）的实例数每帧本该清零，靠的是翻译器拿出来、由宿主在派发前代做的「首个线程写入」（first_store）。反射里 first_store 的 `reg` 是着色器内存储缓冲的序号（绑定项的 `index`），宿主却当 NVN 存储槽用（`S.ssbo[5][reg]`）。这个着色器 5 个存储缓冲 index 0..4 对应槽 4/2/0/1/3，清零写到了槽 0 的别的缓冲上，实例数每帧 +40 从不归零，那一笔越画越重。

**做法**：`nvn_refl.m` 解析 first_store 时按同一份绑定表把 index 换成该项的 `reg`（NVN 槽）。修在宿主，已出的包换新宿主即生效、不用重出。回放：实例数恒为 40，那一遍 127 ms → 1.5 ms，整帧 182 → 48 ms。单测 `t_nvn_first_store` ⑥：旧实现写进槽 0、槽 4 得 out[2] = 1。翻译器 Dsh.cs 的注释「reg = 存储缓冲槽，即 index」不成立（index ≠ 槽时），以后照宿主口径读。

**现象**：11-09 #299 塞尔达无双封印战记（04003F40232DE000）iPad 一进 nnMain 就 SIGSEGV 地址 0（pc sdk+0x634024），5 局同点。

## 分核选「容量最高的前两颗」不要求同档，异构单核旗舰机型绑错核（安卓，issue #48 M2）

**根因**：

**实验数据**（期望 → 真结果，旧仓同一份源码实测）：  
- 9000，Wonder 测试包，同包依次 mode0 / split / mode0 / split 各一局喷泉 180 秒，帧率 34.5 / 29.2 / 35.4 / 24.2 fps（热状态 3、充电，局间温度上升且构图不同，差值不能归因选核、不计正式验收）；同周期只读快照 CPU0–3=200、CPU4–6=838、CPU7=1024，旧 split 两角色落 CPU7 与 CPU6

- 宿主：policy_test 构造 9000/8E 实测拓扑断言 split/split2 在最高组单核时回退、双核时取同组两颗，修复前 9000 断言红、修复后全绿；Linux 亲和夹具（affinity/inheritance/aaudio_route）同红同绿

**做法**：  
split/split2 仅在当前允许集合的最高 capacity 组至少两核时按核号降序分配两个角色，否则回退系统调度（`fallback reason=highest-group-single`）；掩码读取、请求后读回、前后台恢复及外部漂移保护不变。设备实测选核与同场景性能效果仍需新包验证。

## 条件渲染不能在下一次提交开始时忘掉尚未完成的时间戳报告

**现象与读数**：11-10，Mac M5 Pro，基线 `9f7a9aa9f`。正式 `native-test-nvn_rc_pending` 用真实 Metal 共享事件阻塞 A，A 记录时间戳报告，B 随后记录条件清红；报告计数应先归零，使 B 保留初始蓝色。Metal 3 / Metal 4 各 6 项，旧实现各 1 项失败：16/16 GPU 像素全红，期望全蓝。候选两路各 6/6 通过；完成后 CPU 将计数重置为 1，条件清红仍通过。仅撤掉跨提交报告查询，两路再次各 1 项失败；原报告表检查 5/5 通过。

**根因**：`g_rc_npend` 在提交开始时清空，但前一提交的报告直到 GPU 完成回调才写回 CPU 内存。后一提交在此期间求值，会读到报告前的旧计数。Ryujinx 的条件渲染保留 counter event，CPU 求值前先刷新报告；直接读未完成报告的旧内存不等价。

**做法与边界**：按报告地址与提交栅栏保留尚未完成的时间戳报告，其计数字段已知为 0。完成回调写回报告并推进 `g_done` 后，恢复读取 CPU 内存，允许 CPU 请求下一次清屏；不增加 GPU 等待。该回归证明跨提交条件清屏的独立机制，不代表已通过游戏画面或 iPhone 验证。

## 遍内自采样：第一笔自写采样整张拷快照，手机热机每帧能耗涨 5–26%
**现象**：11-09 #307（同遍自采样一律隔离）合入前实测：我方 iPhone 旷野之息热状态 2 时每帧焦耳比旧路径高 +5.3% / +9.2% / +26%，帧率低 2–7%，内存多 80–220 MB；Mac 同局第 ④ 步约 8.5 次/帧、约 50 MB/帧。

**根因**：快照几乎都来自每个渲染遍的第一笔自采样绘制。此时遍还没开，或刚按「载入」打开、本遍还没画过（dirty=0），⑤ 片上读取只在 dirty=1 时尝试，于是整张拷快照。另外 g_fb_dirty 只在开遍时清零、结束遍不清：遍结束后下一遍的第一笔仍看到旧的 1，既不走片上读也不当成内存可读，同样落到 ④。

**做法**：瓦片里正好是「这一笔之前」的内容时一律走 ⑤，分三种：本遍画过；本遍按载入打开、还没画过；遍还没开时，让这一槽开遍必须载入（g_fb_want_load，跳过「不载入」与「整屏覆盖跳过载入」），这一笔不走延后与合并。另外 fb_prepare 在遍未开时清 g_fb_dirty。开遍后核要求的槽确实按载入打开（RED_ONCE 178）。读数（Mac 旷野之息，每 300 帧）：④ 2522–2728 次 / 13.9–16.1 GB → 358–622 次 / 2.4–5.5 GB；剩下的是着色器不在本像素读（同像素证明不成立）的笔。惊奇 #296 实局第 6000–9000 帧 31 张截图纯黑块 0 张。

## ANativeWindow_setBuffersGeometry 后 getWidth 报告的是缓冲尺寸；native_window 没有 SCALE_FIT

**现象**：直连交换链按游戏输出尺寸出图（`ANativeWindow_setBuffersGeometry`）时，两处平台语义与直觉相反：①调过之后 `ANativeWindow_getWidth/getHeight` 报告的是缓冲尺寸，不再是窗口/view 的像素尺寸；②`native_window` 的缩放模式只有 SCALE_TO_WINDOW / SCALE_CROP / NO_SCALE_CROP，没有等比 fit——缓冲按 view frame 双轴独立拉伸。

**根因**：缓冲尺寸是生产端属性，`getWidth` 反映的是它；AOSP `system/window.h` 的缩放枚举止于 `NATIVE_WINDOW_SCALING_MODE_NO_SCALE_CROP=3`，等比只能由 SurfaceView 的 frame（布局尺寸）本身提供——SurfaceFlinger 把缓冲拉伸到 view frame，frame 宽高比 = 缓冲宽高比才不变形。

**实验数据（期望 → 真结果）**：macOS 宿主 fake-Android 桩（tests/hostvk），基线 `3eb3318`：桩按真实语义让 `setBuffersGeometry` 之后 `getWidth` 报告缓冲尺寸，窗口尺寸判定与建链尺寸记录若继续用 `getWidth` → 期望误判为窗口 resize/把缓冲尺寸当窗口像素，真结果按此桩复现；改用租约 `s2a_wsi_state`（surfaceChanged 的 frame 像素）+ 建链时记录窗口像素后 → 期望判定一致，真结果宿主测试全绿。view 布局未在宿主覆盖，真机观感列入 B 批设备验证。

**做法**：`debug.s2a.buffer_geometry=1` 时 present 按渲染目标尺寸出图并退休重建交换链（extent=目标尺寸，整幅时等比 blit 退化为 1:1）；窗口尺寸判定在开关开时读租约 frame 像素而不是 `getWidth`；Java 侧把 SurfaceView 布成缓冲同比例的居中矩形，替代 GPU 等比 blit 与黑边清屏。（尺寸目标从 crop 改成渲染目标、触摸层退回整窗是 #203 复审修正，见下条。）

**补充（同一 API）**：`setBuffersGeometry` 返回 0 不证明缓冲尺寸已改——平台可能不兑现、驱动也可能按 surface min/max 把 extent 夹到别的值。兑现与否必须用调用后的 `getWidth/getHeight` 复核再付销毁+重建代价；宿主桩模拟「返回 0 但 `getWidth` 不变」时，先销毁重建的顺序会每帧重复「销毁→重建→extent 仍不等于输出尺寸」（宿主实测 `g_geo_calls` 逐帧增长、`g_destroyed_swapchains` 不为 0）；复核失败记 `geometry_failed` 退回普通等比 blit 后，同一用例 1 次请求、0 次重建（期望 → 真结果一致）。

## macOS 自带 awk 的中文字段相等比较不可信：「同」也能判成「新」

**现象**：`tools/contrib_check.sh` 的红步与基线对照里，awk 按 `$1 == "新"` / `$1 == "同" || "超" || "缺"` 给机读行分类。在 macOS（自带 awk 20200816、UTF-8 locale）上，摘要把「与基线同红」的步误打进「新红」行，同时「未证」机读行把真新红的步也算了进去——两边都漏分。同一脚本的 `grep -c '^新	'` 计数是对的，出现「计数说新红 0 步、新红行却列了一串」的自相矛盾。

## Android 16：pm path 未装包返回 rc=1 空输出，拿 rc=0 判「查询成功」会起局前就红

**现象**：Android 16 真机上 `android/tools/run_game.py` 起局第一步就红：`install_state()` 用 `adb shell pm path <pkg>`（默认只放行 rc=0）查安装状态，未装该包的设备返回 rc=1、stdout/stderr 皆空，直接 RuntimeError，任何路径进不了局。旧机型 `pm path` 未装包回 rc=0 空输出，同一代码在旧机上正常。

**根因**：`pm path` 的返回码语义在 Android 16 变了——未安装从「rc=0 无输出」变成「rc=1 无输出」。把 rc=1 一律当 adb 失败处理会把「未安装」误判成查询失败；反过来把 rc≠0 一律当「未安装」会把 adb 层错误（设备断线、pm 崩溃，常带 stderr）误判成没装 → 真机上照装、收局复查同样被误导。

**实验数据**（期望 → 真结果）：Android 16 设备未装包 `pm path org.s2arm.game.t…` → 期望 rc=0 空输出，真结果 rc=1 空输出（adb 壳层无 stderr）；宿主替身同一语义下，旧实现全量「未安装」路径用例红 8 例，新实现 20 例全绿。负对照：判定里去掉 stderr 条件 → rc=1 带 stderr 的掉线场景被当未安装放行（应红变绿）；rc≠0 一律当未安装 → rc=255 查询失败被吞（应红变绿）。

**做法**：`pm path` 按三态判——rc=0 按 `package:` 行数判装没装；rc=1 且 stdout/stderr 皆空 = 未安装；其余（别的 rc、带 stderr）= 查询失败抛错，入局前直接红、收局复查失败按还原未证留置。`adb shell` 的 stderr 要单独拿（`d.shell` 只回 stdout），用 `subprocess.run([*d.argv, "shell", ...], capture_output=True)`。

## adb.shell(整串带管道) 经 shlex.join 被包成一个词，设备端 rc=127；替身若二次拆词会假绿

**现象**：`android/tools/deploy_game.py` 的设备端 SHA 核验改成 `find … -print0 | xargs -0 -n 256 sha256sum` 后，qa-fone 复审指出：这条管道以单个字符串实参传给 `Adb.shell(...)`，真机上会 rc=127 `command not found`，但宿主测试全绿。

**根因**：`Adb.shell(*args)` 内部走 `Adb.call('shell', shlex.join(map(str, args)))`——带空格/竖线的整条命令被 `shlex.join` 单引号包成 **一个 shell 词**，设备 `sh -c` 把这个词当可执行文件名 exec，必然 127。宿主测试的 fake adb 起初「宽容」地对 len==1 的引号串又做了一次 `shlex.split`，管道被解开照常执行——替身比真机宽松 → 假绿。这是第二例「替身语义比真机宽」的坑（首例见上方 pm path 条目）。

**实验数据**（期望 → 真结果）：宿主 `sh -c "'find /x -type f | xargs sha256sum'"` → 期望按管道执行，真结果 `sh: find /x -type f | xargs sha256sum: command not found` rc=127（macOS zsh/sh 均复现，Android toybox sh 同语义）。修复后 `adb.shell('sh','-c', 脚本)` → rc=0、603 文件分批核过。负对照：实现退回 `adb.shell(整串)` → 大资源树用例立刻红在 127，与真机一致；替身退回二次拆词 → 同一假绿复现。

**做法**：凡是要让设备 shell 解释多词/管道的命令，一律显式 `adb.shell('sh', '-c', <脚本>)` 三段传，别把整条命令塞进一个实参。替身侧钉死真实语义：`shlex.split` 后 len==1 且词内含空格 → rc=127 `command not found`；`sh -c <脚本>` 解包脚本再切词；裸 `|` 只在 `-c` 脚本里才算管道。新增 `test_fake_adb_shell_single_word_is_127` 负控把这条语义钉住（run_game_test.py）。原则：**替身先按真机语义写，再让它服务断言**——假替身比真机宽容是这类假绿的共同根因。

## adb exec-out 拉私有证据只看 rc=0：空读/截断传输/同 PID 旧文件会被当本局完整证据

**现象**：`android/tools/run_game.py` 的 `collect_private_logs` 第一版只按「文件名里的 PID ∈ 当局 session_pids」过滤、`exec-out run-as cat` 拉回字节只看 rc=0。qa-fone 复审 r14 指出三个口子：① PID 复用后旧局/旧进程写的 `host-*-<pid>-*.log`、`frame-log-<pid>.log` 会混进本局证据；② exec-out 传输空读（rc=0 零字节）或截断短读会被当完整文件落盘；③ READY 前异常 `pids={}` 时 finally 把全部候选过滤光，死前宿主日志——正是失败现场证据——一个都拉不回。

**根因**：设备 `sh` 的 rc=0 只证 `cat` 执行过，不证拿到的是完整文件（run-as 权限变化、截断、空文件都可能）；PID 只是整数，文件名绑定证明不了「这个文件是这个进程实例写的」——要进程出生证（`/proc/<pid>/stat` starttime jiffies 折墙钟 = birth_wall_s）配 mtime 门：mtime < birth_wall_s 的文件早于本次进程出生，不可能归本局（与 `SessionLogEvidence.capture` 的 `lastModified >= birth.startWallMs` 同模型）；READY 前失败拿不到 session_pids，要退化成「起局时间窗 + 文件名 PID」收证并如实标 unproven。

**实验数据**（期望 → 真结果）：宿主替身负对照三组——去掉源端 sha256sum+wc 对拍 → 截断传输（rc=0 半文件）记录 verified=True（应红变绿）；去掉 mtime/birth 门 → mtime 早 100000s 的同 PID 旧局文件被当本局证据拉回（应红变绿）；pids 空退回全过滤 → READY 前失败局 host_logs 零文件（应红变绿）。修正后 run_game_test 43 例全绿，含 birth_ticks→birth_wall_s 折算断言。

**做法**：私有证据收证三段——① `run-as sha256sum <p>; wc -c < <p>` 先记源端字节/SHA，exec-out 拉回逐字节对拍，不符或拉回零字节一律 verified=False 记注（manifest 记双侧 `device_bytes`/`device_sha256` 对拍）；② 归属 = 文件名 PID ∈ session_pids 且 mtime ≥ birth_wall_s − 2s（USER_HZ=100，birth 是唯一归属锚，拿不到一律 unproven，起局墙钟不充数）；③ `pids` 为空（READY 前异常）退化按起局窗+文件名收证、session=unproven，零候选也写明「失败现场证据未证」——收不到要记，不静默。替身旋钮：`priv_empty`/`priv_truncate`/`data_mtime`/`die_before_ready`/`no_priv_seed`/`no_proc_stat`。

**复审续（r15）**：归属判定第一版仍有口子——`session=bound` 只看 `pids` 非空：`birth_walls` 缺该 PID 退回起局墙钟、两头都缺就跳过 mtime 判据、`stat` 被拒 mtime=None 也跳过——等于归属「证不了就当证了」。qa-fone 独立负控：同 PID 文件 + birth/墙钟缺失 + stat denied → 实得 `verified=true`/`session=bound`/`notes=[]`。修正为 fail closed：bound 要求 mtime 实读且过窗（stat 拒/birth 墙钟两头缺 → unproven + 注记写明哪一环证不了），`host-<seg>-<pid>-*.log` 另做名实互核——文件首行 `[s2a] Android 会话日志：session=<seg> pid=<pid>`（runtime/src/os.c `s2a_android_session_log_start` 的 dprintf）与文件名逐段对上才升 bound，对不上（改名/拼接的证据）照拉但 unproven + 注记。替身补 `priv_stat_denied`/`no_wall`/`no_proc_stat` 旋钮，负对照实测三处都咬人。

**复审续（r16）**：起局墙钟兜底本身就是口子——它只圈「本局时间窗」、证不了文件属于哪个进程实例：birth 缺时 mtime ≥ 起局窗的同 PID 旧文件照样升 bound。修正：birth_wall_s 为唯一归属锚，`/proc/<pid>/stat` 缺或读拒一律 unproven（墙钟正常也一样）；READY 前异常（pids 空）的退化收证不受影响——那路本来全部 unproven。负对照：birth 缺给兜底锚 → no_birth 用例红。

## 已装包数据保护四处口子：tar 回灌不验、不可访问当不存在、pm clear 抢跑、降级看 usage 文本

**现象**（qa-fone 复审运行器 #160 备份/还原路径指出）：① `restore_data` 只在解开之后对 `find -type f sha256sum`——tar 归档本身没在宿主机解包核对过，清单也只记普通文件，软链/空目录/权限位丢了没人发现；② 备份探针 `[ -d dir ] && echo yes` 两态：目录存在但 run-as 进不去时与「不存在」同支，数据被静默跳过不备；③ `pm clear` 在函数开头就跑——归档烂了也先清光了设备数据；④ `device_allows_downgrade` 拿 `pm` usage 文本判「支持 -d」，usage 写了不代表真让装（INSTALL_FAILED_VERSION_DOWNGRADE 是装的时候才炸）。

**根因**：保护手段都只防「顺利路径」——核对没放在破坏性操作前面，存在性探测不区分「没有」和「进不去」，能力判定看文档不看实测。

**实验数据**（期望 → 真结果，宿主替身负对照）：`pm clear` 提到核对前 → 单测「核对未过 pm clear 不许跑」红（pm clear 已执行）；探针退化成 denied=absent → denied 用例红（denied 目录被跳过只备 2 处、局照跑照还原）；`probe_downgrade` 恒 None → downgrade_unsupported 用例红（跑完局装回原包 `install -r -d` 才炸、设备留置）；解开后不验 → pushed_tamper/corrupt_restore 两用例 RESULT=done 假绿变红。

**复审补刀**（qa-fone b88/r16/r17 复审 + 8E 真机实测，更深层的坑）：⑤ `[ -e path ]` 也是假三态——**父目录不可搜索**时它和「不存在」一样返回假（8E run-as 受限父目录、宿主 `/private/var/root/.` 实测：`ls` 拒权但探针报 absent），`[ -e ]` 探针照样把受限目录静默当 absent；改 `stat -c %F path 2>&1` 接 stderr 分 EACCES/ENOENT，分辨不了的一律 denied。⑥ toybox `tar -cf - -C dir .` 首成员是 `./`——Python tarfile 读出名归一成 `.` 进清单键，而设备端 `find -mindepth 1` 天然不含根，归档与源清单每局必差一项假红；成员名统一 `posixpath.normpath` 后跳过 `"."`/"" 根项（替身 tar 同款补 `./` 首成员，回归固化）。⑦ 同版 `install -r -d` 成功**证不了真降级**——同 versionCode 不触发版本排序，flag 被解析层收 ≠ 降级真的让装；且它在备份前就改了包状态。修法定案：**入局前不做任何装包探针**——fwd 方向（原包 > 新包）真降级就是装测试包本身、`install -r -d` 失败即拒（装失败不卸旧包）；back 方向（原包 < 新包）入局前证不了能装回 → 连拉/装都不做直接拒跑（先升级入局、收局再试降级 = 装了赌能降回去，qa-fone #323273 裁定）。替身 install 按 versionCode 排序：apk_vc < 已装 vc 才是真降级（同版 -d 照过、降级 -d 在 `pm_no_downgrade` 下拒），直验用例钉住这条区分。⑧ `pm clear` 用 `allowed=(0,1)` 不看结果——clear 失败照样 `find -delete`+回灌；改硬门：rc=0 且输出 `Success` 才往下走，否则立即失败+留置（不回灌不删目录，设备数据原样）。⑨ 私有证据「本局」锚：文件名 seg/首行 session 只是 services `session_id`(uint64) 名实互核，不证明文件属本局；补 `runtime-library.json`（Java 起局写 state_dir 的 `{pid, sessionId}`）——sessionId 必须等于 READY 行 `session <uuid>`，锚缺/对不上 → unproven。

**做法**：清单升级 schema 2——`stat -c '%a|%F|%n'` 全量成员 + `find -type l` 软链目标 + `sha256sum` 文件哈希；备份落盘即宿主机解包逐项核对（对不上 Refuse），`restore_data` 顺序硬门：归档核对 → `pm clear`(rc=0 且 Success) → 回灌 → 设备端同口径复核；三态探针改 `stat` 接 stderr（ok/absent/denied，denied 一律拒跑），卸载后外部目录同款、ENOENT 才算已清其余一律 denied；tar/源成员名 `posixpath.normpath` 归一并跳过根项；降级不看 usage 不看同版重灌——fwd 由装测试包 `install -r -d` 实测、back（原包 < 新包）入局前直接拒跑；私有 bound 由文件内容 `session_uuid` 实证（⑫）。⑩ mtime 容忍窗会假 bound：`mtime < birth - 2s` 的 2 秒余量让「同 PID 旧局、mtime 恰在窗内」的文件照样 bound（负控：birth-1s 旧文件实测入证）；判界收紧为严格 `mtime ≥ birth`。⑪ 原包备份与打包中间产物用 `tempfile.mkdtemp()` 落系统 /tmp——逃逸 out 保留策略且崩溃即泄漏；归位 `<out>/orig-backup`、`<out>/deploy`(pack/resources.tar），成功清再生材料、失败留证记 manifest。⑫ marker↔READY-uuid 对拍仍假 bound：runtime-library.json 是进程写的旁证、不是文件自述——同 PID 旧文件 mtime 落在 birth-2s 容忍窗内 + marker 全对上照样 bound（qa-fone #323682 反例）。本局锚改**文件内容**：运行器起局前 `setprop debug.s2a.session_uuid <uuid>`（每局随机号，os.c 会话日志首行 `uuid=`、nvn_vk_frame_log meta 行尾 `uuid=` 都写它），bound 要求文件自述本局号——旧文件造不出；字段缺/不符 → unproven。`stat -c %Y` 整秒对 birth 浮点判不了先后（birth=1000.5、新文件 mtime=1000.7 会被旧判据当旧局漏拉）——改不跳过照收证，先后由 uuid 裁决。⑬ 收尾顺序：orig.apk 清理排在 logcat 停验之前 = 核验未过备份已没（人工救不回来）；`orig_tmp.unlink()` 裸奔 OSError 直接崩穿 finally 吞掉 manifest/锁释放。修：备份清理挪到所有还原核验之后、fails 非空必留，`unlink`/`rmtree` 全包 try/except 记账继续（替身 `pull_dir` 负控：备份路径成目录 → unlink 抛 IsADirectoryError/EPERM，裸奔版进程直接挂死 manifest 缺失实测红）。替身补 `data_links`/`data_subdirs`/`data_modes`/`data_denied`/`ext_denied`/`ext_parent_denied`/`data_parent_denied`/`corrupt_backup_tar`/`corrupt_backup_before_restore`/`pm_clear_fails`/`pm_clear_silent`/`no_runtime_marker`/`marker_uuid`/`no_log_uuid`/`log_uuid`/`pull_dir`/`pull_stray` 旋钮，与 `[ -e ]`/`./` 根成员/versionCode 排序真义建模。⑭ qa-fone #324194 四处：a) 首行插 `uuid=` 字段把 SessionExitEvidence 的 `pid=<n> file=` 紧邻正则顶断（新 APK 正常收局被误判 PID mismatch）——解析改 `pid=<n>(?: uuid=\S+)? file=` 新旧首行都认（Java 单测补新首行正例 + 错 PID 负控）；b) 帧块证据链原来只按 logcat 行 PID 圈——同 PID 别局转储会混进帧表；meta 行本就带本局 uuid（emit 同文双写），升硬绑：`uuid=<run_uuid>` 才进帧表，缺/不符整段不收、`manifest.frame_log.binding` 记「uuid+PID」（负控：摘门 mismatch 块实测入表）；c) `unlink` 与父目录 `rmdir` 一个 try——文件删成目录删不掉时 except 报「原 APK 留存」，文件/目录状态记串；拆开记账（文件留记 `orig_apk_backup`、仅目录留记 `orig_backup_dir`，`pull_stray` 负控实测合并版报假留存）；d) session-log 宿主测试 `-D__ANDROID__` 编 os.c 没有 bionic 头——`sys/system_properties.h` 改 `__has_include` 守卫（svc_mem.c 同款模式），测试侧补语义同真 bionic 的 env 源替身（缺→0、有→拷值返回长度），新增 uuid 用例正控首行字段、success 用例钉 `uuid=-`。

## 游戏库在外置盘时出包清理报「目录非空」（Errno 66，#369）

**现象**：游戏库放在外置 APFS 盘上出 Mac 包，界面布局阶段 `rm` 报 `roots/<款>@….tmp/romfs/…: Directory not empty`，解包阶段 `shutil.rmtree(extraction)` 报 Errno 66；同样的文件放内置盘就成功。玩家关了 DSDontWriteUSBStores，游戏库里仍出现 .DS_Store。

**根因**：删目录是「先删里面的文件、最后删空目录」两步；中间若有程序往这个目录写东西（访达在打开的目录里写 .DS_Store，非 APFS 盘还会有 ._ 附属文件），最后那步就报目录非空。原先一次失败整单失败；解包那处还直接调 `shutil.rmtree`，绕过了统一删除入口。玩家机上写入的是不是访达没有核实。

**读数（期望 → 真结果）**：Mac 本机复现：`shutil.rmtree` 期间另一个线程往目录写 .DS_Store → Errno 66。单测：删的同时被塞进 .DS_Store / ._x → 新码删干净（旧码红，报的正是 Errno 66 / Directory not empty）；塞的是普通文件 → 不硬删、报错点名该文件。

**做法**：作业层统一删除 `library._rmtree` 遇到删空目录报 ENOTEMPTY，只清系统自动生成的文件（`layout.os_junk`）再删，最多 5 次，剩别的文件就报错点名；`ensure_extract` 改走 `_rmtree`。shell 的 `pack/roots.sh _root_rm` 同样处理，名单进 `tests/os_junk_sync_test.sh` 四处一致核对。
## iPhone 开发者模式不能只凭设备列表判关闭（issue #373）

**现象**：已配对的有线设备在列表里是 `developerModeStatus=disabled`、详情是 `enabled` 时，安装和装机清单均提前提示打开开发者模式。

**根因**：`device_link()` 在查询详情前就按列表的 `disabled` 返回；后续开发连接流程也丢弃详情 JSON，再读可能仍滞后的设备列表。

**读数（期望 → 实测）**：基线 `966bb22e`，合成设备夹具分别走安装 / 轮询，共 2 个场景；详情已开启应继续 → 修前两例均返回 `developerMode`，修后 2/2 继续。安装单测 79/79 通过；进程内换回基线实现，4 条关键测试重新触发 13 处断言失败、0 异常。真实关闭、查询非零退出 / 超时 / 系统异常、详情身份不符 / 缺失状态、开发者服务二次复核同测。这些夹具不代替真实设备重连验收，也不证明 Apple 内部具体缓存机制。

**做法**：列表报关闭或开发连接未就绪时，对选定设备做有界详情查询，以同身份详情替换设备和诊断快照。只有详情明确关闭才提示开启；查询失败或回包不完整时报开发连接失败，清单中开发者模式保持等待、不误打勾；确实关闭时不更新开发者磁盘映像。
## RomFS 存储清扫不持锁时会删掉刚收纳的新身份（11-09）

**现象**：`tests/roots_romfs_sweep_race_test.sh`「不持锁的清扫」满载下偶发红：并发提交刚收纳的 RomFS 新身份被清扫删掉，提交完的现行 romfs 读不到。

**根因**：`pack/roots.sh root_romfs_sweep` 单独调用时不拿提交锁，只靠「删前再读一次链接」防并发收纳。再读时先按 `g@*` 列出各版本、再逐个读 romfs 链接；并发的提交恰好在这之间把 `g@<标签>.tmp` 改名成 `g@<标签>`，`.tmp` 已不在、正式名又不在已列出的名单里，新身份被当成无主删掉。提交里调的清扫本来就持锁，不受影响。

**读数（期望 → 真结果）**：测试按事件把这一刻钉死（清扫为新身份再读、读到 `.tmp` 时放行提交改名，提交切现行前等清扫做完）：原版 roots.sh 每次都删（空载 4/4、8 个忙循环满载 6/6）；修后满载 12/12 绿。

**做法**：清扫一律持这一款的提交锁（`root_commit` 里已持本款锁就不再拿；`_root_lock` 记下锁的是哪一款），与收纳、提交串行；拿不到锁这一款跳过、一个不删。持锁后「再读一次」没有意义，删掉。教训：靠「删前再核一次」防并发，核与删之间仍有空当，互斥要靠锁。
## 服务测试必须自行登记应用元数据，并恢复缺项负测前的原对象（11-10）

**现象**：Mac arm64、基线 `fcee2f315`，不提供外部游戏数据运行官方 `services/gate.sh`，主流程执行到 pctl 批次用例创建对象时，`ApplicationLaunchProperty.GetByPid` 取不到进程元数据而空引用；476 项中 1 项不符，后续用例未执行。

**根因**：测试直接 `Host.Boot`、`Exports.Register`，应用登记只在可选的外部游戏数据存在时执行。LDN 用例会临时登记并清除 PID `0x51` 的 `ProcessResult`，后续 pctl 测试却依赖该项；缺项负测还会删除已有登记项，再造同程序号对象替代。完整 `Application.Register` 同时登记 GPU 内存等状态：已有真实游戏时，在主流程中再调用会由 `GpuContext.RegisterProcess` 抛出 `The PID was already registered`。仅恢复进程元数据无法隔离完整应用登记。正常 Native 入口在开放服务前完成登记；这里修的是测试前置与隔离。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0，复用现有 `Homebrew.npdm` 与 ARP 资源准备逻辑，在独立新宿主运行 pctl 真实登记，3 项、0 不符；只撤登记调用，2 项均红；恢复后 3 项、0 不符。官方完整入口无外部游戏数据时，93 个独立模式通过、主流程 482 项 / 0 不符。真实登记的 LDN 独立模式 19 项、0 不符；只把原对象恢复换成重建，19 项中 1 项不符，程序号仍相同但对象身份为 `False`。固定 `a55512d84` 加入程序号 `01006F8002326000` 的真实 3.0.3 数据复现重复 PID 异常；隔离 pctl 后完整入口从 524 项 / 3 不符变为 529 项 / 2 不符，重复 PID 异常消失、后续用例执行。剩余两项分别是缺旧着色器缓存夹具及实际 DLC 5 项与用例预设 2 项不同，未改检查或将该次完整入口称为全绿。

**做法**：需要完整应用登记的 pctl 用例通过已有 `[SoloTest(..., Booted = true)]` 在独立宿主执行一次登记，并核对 PID / ProgramId；LDN 缺项负测以 `finally` 恢复进入前的同一个 `ProcessResult`，并核对身份与程序号。不为生产增加默认成功、空值回退或重复 PID 例外。

## Windows 出库 rc=127 被一律译成盘满（11-09）

**现象**：Windows 出包机出库失败，报红行写「127 = 盘满（STATUS_DISK_FULL 0xC000007F 低 8 位）」，错误分类跟着归成 disk_full；实际 T 盘还剩 127 GB，维护方照提示删了 37 GB 可再生缓存，问题没变。

**根因**：`direct_lib.sh` 在 Git Bash 上见到出库 rc=127 就当成 0xC000007F 的低 8 位。可出库程序自己异常退出（这次是测试树里诊断替换写错，dsh_batch 抛异常）也是 127，退出码本身分不出两者。

**读数（期望 → 真结果）**：Mac 本机单测 `tests/direct_lib_rc127_test.sh`（函数原样从 direct_lib.sh 抽出，uname 换桩造 Git Bash，余量用 S2A_DISK_FREE_G 注入）：余量 127 GB、build.log 是普通异常 → 「不是盘满」、错误分类不归 disk_full；build.log 有 .NET「There is not enough space on the disk」→ 盘满；剩 1 GB → 多半是盘满；量不出余量 → 两种都说、不归 disk_full；7 项全过。

**做法**：`rc127_note` 先看 build.log 有没有盘满原文，再看临时目录 / 缓存所在盘余量（< 2 GB 才说多半是盘满），余量够就明说不是盘满并多贴 build.log 末尾（20 行）；量不出余量不下结论。教训：退出码低 8 位撞号时，判因要靠日志原文和现场余量，别只看码。
## Windows 播种大款后目录改名被拒（WinError 5），且播种半小时没有进度（#361）

**现象**：Windows 0.2.1 出一款 Switch 2 大款（解包 20.6 万个文件、23.5 GB），进度条停在「解包 100%」约 30 分钟，随后在把 `…@seed-….tmp` 工作目录改名时报 `PermissionError: [WinError 5] Access is denied`，整单失败。

**根因**：播种（`pack/orch/refresh.py seed`）逐个拷完几十万个新文件后，提交事务要改几次目录名（RomFS 收进共享存储、`.tmp` 改正式名）。杀毒 / 索引程序扫描刚写完的文件时开着句柄，Windows 上只要目录里有文件被开着，目录改名就被拒；原先一次失败整单失败。播种阶段又没有任何计数，看着像卡死。占用者是谁没有在玩家机上证实。

**读数（期望 → 真结果）**：Mac 本机单测，`roots` 模块看到的 `os.name` 换成 nt（不改全进程）、`Path.rename` 换桩：前两次 WinError 5 后成功 → 改名成功、睡了前两档；一直被拒 → 重试满约 1 分钟后报错，原文点名目录并建议加杀软排除；非 Windows / 其它 WinError 不重试；播种 4 个文件 → 进度文件末行「播种 4/4」。orch 三份单测全过。

**做法**：`roots.rename_dir` 统一做目录改名，Windows 上 WinError 5 / 32 按退避（0.1 s 起到 30 s，合计约 1 分钟）重试；提交 / 收纳 RomFS / 重放 / 一键出包整目录搬 RomFS 的改名都走它。播种按出包进度协议写「播种 已拷 / 总数」。

## 删除等待锁的测试不能把子进程定时退出当作父进程计时起点（11-10）

**现象**：`test_delete_waits_for_execution_lock_held_by_cancelled_task` 让真实子进程持锁、打印就绪后睡 3 秒；父进程读到就绪后才计时，并要求删除至少等待 2.5 秒。固定 main `90295d850` 的原样 48 份检查可通过，但这个断言依赖父进程及时得到调度。

**根因**：子进程的 3 秒从打印就绪时开始，父进程的计时则晚于读取就绪；两者之间被调度延迟时，锁的剩余寿命缩短。生产删除每 2 秒重试一次，正确等锁到下一轮成功也可能只用约 2 秒，违反测试的 2.5 秒下限。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0，仅在原测试读到就绪后、计时前用调试跟踪对测试进程 `SIGSTOP` 2 秒再 `SIGCONT`，真实持锁子进程继续运行；原测试应守住等待语义 → 因 `2.015 < 2.5` 失败。改用显式释放及实际等待事件后，相同调度扰动 1 项通过；临时撤掉生产删除的执行锁这一处，1 项按「删除在报告持锁等待前返回」失败，恢复生产后 1 项通过。维护者 #340 的两份首红日志位于其本机，当前无法读取，不能认定它们与此竞争同因。

**做法**：真实子进程持锁直到 stdin 收到释放信号；从工作线程调用真实删除，先观察其等待阶段事件并确认目录清单尚未删除，再释放锁并验证操作完成。超时仅用于界定测试卡死，不再用父子进程不同起点的耗时下限证明等待。

## 两个作业同时收私有目录日志，catalog 偶发「任务所需的文件或目录不存在」（11-09）

**现象**：启动器单测 `WorkerIntegrationTests.testRealWorkerDrainsFastResultsAndCanReadItsLibrary` 偶发超时，`store.error` 为「任务所需的文件或目录不存在。」；main 合入后全套两次红在这里，守望二分分别定到一个纯文档提交和一个崩溃重抛提交，两者都碰不到它。

**根因**：每个作业起跑都执行 `layout.ensure` → `adopt_private_logs`，把私有目录里的日志收进库。用例中途新建的第二个 `Store` 初始化时会自己 `refresh()`，于是两个 catalog 并发；A 判完 `src.is_dir()`，B 已把收空的 `private/logs` 删掉，A 再 `iterdir()` 抛 `FileNotFoundError`，整个作业失败。玩家启动器同时起两个作业也会撞上。

**读数（期望 → 真结果）**：setup 后同时起两个 catalog，修前 21 次红 1 次（调用栈落在 `layout.py adopt_private_logs` 的 `src.iterdir()`）→ 修后 60 次 0 红；确定性单测（判完 is_dir 后目录消失）旧码红、新码绿。

**做法**：被并发作业先收走的目录当作已收完（`iterdir` 的 `FileNotFoundError` 跳过）；`core.prune_jobs` 同样容忍列目录后目录 / 文件被搬走。教训：守望单次二分落在碰不到失败点的提交上，先按「不稳定」复现，别直接认肇事。

## 错误摘要把同一原包按内容记录重复计数（issue #128）

**现象**：同一原包在 catalog 中分别提供 base、update 记录时，错误摘要保留两条包明细，也把原包合计算了两次。

**根因**：`report.game_lines()` 直接累加所有 `packages[].size`，没有按 catalog 的 `sha256` 来源身份去重。

**读数（期望 → 真结果）**：Mac arm64、基线 `c36447f97`，临时 catalog 中两条共享来源、各记 4096 字节的包记录；原包合计应为 4.00 KB → 修前 8.00 KB、修后 4.00 KB，两条包明细保留。摘要测试 10/10 通过；换回基线实现后 4 处断言重新失败。同身份不同路径、不同身份同路径、无路径、缺少或空身份同测。

**做法**：只对非空 `sha256` 的来源去重，缺少身份的旧记录仍分别累加；使用 catalog 已存大小，不读取原包文件。
## 打包纹理的附件与 image 写入要参与局部重上传保护（11-10）

**现象**：256×256 RGBA8 打包纹理先由真实 GPU 整张写红，CPU 随后只把 `(0,0)` 写绿；另一宿主页的 `(255,255)` 却恢复成初始蓝色。

**根因**：附件绘制与 image store 只记全局 GPU 旧字节账，未维护已有 `NvPkg.pgpu`。后续 CPU 局部改页时，已有打包纹理走整张重上传，从旧 guest 字节覆盖未被 CPU 修改的 GPU 内容；首次转成打包纹理的 `carry_gpu` 无法覆盖这个路径。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0，基线 `af2bd1481`，生产 draw 与 rw-image dispatch 各先独立读回确认两角为红色，再验证 CPU 改绿及另一页保红。Metal 3 / 4 各 12 项应全绿 → 修前各 4 红（正常采样和独立 GPU 读回的远端均错回蓝）、修后共 24/24 绿；回退同一写入标记调用后两路各 4 项重新变红。

**做法**：子资源写入入口同时维护全局旧字节账与打包纹理的 GPU 页记录，复用已有部分重上传路径。回归只验证不同宿主页，未扩展同一页内的细粒度 CPU/GPU 合并范围；这些读数不代替游戏画面验收。

**缩小存储边界**：局部重传矩形使用游戏坐标，不能贴到内部分辨率缩小后的存储。Mac M5 Pro / macOS 27.0，`e3d9ed78f` 的 256×192 打包颜色目标缩到 128×96 后，CPU 改一个像素：期望重建 256×192 → Metal 3 / 4 各仍为 128×96（各 1 红）。局部重传增加宽高不小于游戏尺寸的条件后，两路各 4/4 绿：重建原尺寸、GPU 读回更新像素为绿及远端 guest 原字节为蓝、下一渲染遍再缩到 128×96；仅回退尺寸守卫后两路各 1 红，恢复后两路各 4/4 绿。缩小存储沿用整张上传，宽高均足够的存储保留局部上传。
## NVN 结束上一遍不能隔离下一笔的附件自采样（#296）

**现象**：惊奇 1.2.1 的 iPhone 15 Pro Max / iOS 18.6 诊断包（宿主 `c4adca3d0`）记录 Metal 3 直连，每 300 帧常见 600 笔结束遍后采样、快照和片上读取均为 0；报告者在开头移动、跳跃时见闪烁。该日志只能定位反馈路径，不能单独证明闪烁根因。

**根因**：`fb_prepare()` 默认允许写入采样槽的绘制直接读取原纹理。附件未脏时不做隔离，已脏时只结束上一遍；新遍仍会同时采样并写同一资源。只验证特定 GPU 恰好画对像素，会漏掉这个未定义读写路径。

**读数（期望 → 实测）**：Mac M5 Pro / macOS 27.0（26A428）、基线 `92f980f04`，真实生产绘制与参数编码，Metal 3 / 4 各测默认 7 项和强制快照 5 项。自写槽在未脏 / 已脏两例中应绑定独立采样资源 → 修前两路各 2 项失败（采样与附件资源 ID 同为 `0x1`），修后共 24/24 项通过；原始 GPU 像素检查在修前也通过。候选设置 `DM_NVN_FB_SELFREAD=1` 恢复旧路径后，两路均重新出现这 2 项失败。另有 mip 钉级视图回归两路各 6/6 通过。

**做法**：保留已证明可用的片上读取，自写槽其余情况默认采样已有快照；不写采样槽的绘制保留无需拷贝的路径。本次未完成游戏开场和 iPhone 同包 A/B，不把 GPU 单测当作 issue 画面验收；新增快照的真机帧时与能耗影响待测。

## GL 直连预检与翻译器的工具选择不一致（issue #269）

**现象**：`GLSLANG` 指向可执行工具、PATH 没有 `glslangValidator` 时，纯 GL 提前报缺工具，混合 GL 跳过离线库；这不证明 issue 报告者的失败属于同一原因。

**根因**：`direct_lib.sh` 检查 PATH 上固定名称，`gl_shaders.py` 则使用 `GLSLANG`（仅未设置时回退固定名称）。

**读数（期望 → 真结果）**：Linux 容器、基线 `31bfb8d`，合成工具和隔离 PATH，纯 GL 入口与混合 GL 分支各测 9 种情况，共 18 项；空格路径的显式工具应被调用 → 修前两分支均未调用、修后均调用；回退生产检查后两分支再次未调用。未设置变量时的 PATH 回退、无效或空变量和缺 `spirv-cross` 同测。未跑真实 Windows、Mac 出包或游戏复测。

## 帧率上限非整除档：生产端交换间隔下限不能四舍五入

**现象**：通用层 `FramePacingPolicy.SwapIntervalFloor` 原来是 `round(vsync / 上限)`，只认 0/30/60/120 时都整除，结果对。放开到任意档后，上限 40 得 `round(1.5) = 2`，也就是生产端每 2 拍出一帧（30 帧），比用户给的上限 40 还慢。

**根因**：交换间隔 k 在 60 Hz 节拍下给 60/k 帧，要「不慢于上限」应取满足 60/k ≥ 上限 的最大 k，即 `floor(vsync / 上限)`（至少 1）。四舍五入在 1.5 这类半值上往上取，就落到了更慢的一档。

**读数**（期望 → 真结果）：`tests/frame_pacing`「40 FPS floor is 1」改前（round）expected 1, got 2，改后（floor）通过；30 / 60 / 120 的下限两种算法同为 2 / 1 / 1，原有断言不变。

**做法**：下限按 `floor` 取，并用非整除的档（40、24）做断言。上限本身仍由呈现端 `MinimumPresentationInterval` 的 1/上限 保证。

## 文件后备下大块 F_PUNCHHOLE / 大块重映射会拖住整机（11-09，#258）

**现象**：0400486024DEC000 在 16 GB M1 Pro（客体内存文件后备自动开）上每约 30 秒整帧停 1–2 秒；`sample` 显示游戏线程在 `UnmapPhysicalMemory` 里逐 16 KB 宿主页 `F_PUNCHHOLE` + 重映射（`svc_mem.c` pages_release → `vawin.c` s2a_guest_zero），全程持 `g_mu`，音频渲染线程等同一把锁。

**第一版修法踩的坑**：把连续页攒成一段、一次打洞 + 一次重映射。微基准很好（同机 256 MB：1083 → 14.5 ms），但真机上开机就冻 11–65 s（所有线程空等、CoreAudio 回调断）、进场景约 1 分钟 Metal 报 `kIOGPUCommandBufferCallbackErrorHang`（4/4 局）。同一构建关文件后备（`S2A_GUEST_FILE=0`）开机、读档、挂机 260 s 全干净；诊断记账 3536 次释放、0 次落在渲染器在用的零拷贝池里，挂死前 30 s 没有任何释放。结论：不是释放段撞上 GPU 在用的缓冲，而是大块 `F_PUNCHHOLE` / 大块 `MAP_SHARED` 原偏移重映射本身让内核拖住整机。微基准只量了系统调用本身，量不出这种拖到后面才爆的代价。

**第二版也踩坑**：锁内只 `mprotect` 成不可访问并记「待打洞」，打洞交给后台线程按原来的 16 KB 粒度逐块做、不再重映射（分支 claude/project-thread-xxrjo1 @ abd69879）。单测、gate、微基准（256 MB 解除持锁 1093 → 25 ms）都好，真机进场景约 34 s 仍报同一个 GPU 挂死，两次整机冻结时后台打洞线程都是空闲的；关文件后备同样干净。两版修法唯一的共同点是 `UnmapPhysicalMemory` 从约 1 s 变成约 25 ms 返回。

**时序实验定位**：在第二版上让解除线程每次 ≥1 MB 解除后停 1 s（锁内、锁外各一组）：6 分钟都不挂，30 s 周期回来；不停：进场景 1 s 后画面停 6 分钟，`sample` 里后台打洞线程一直在 `fcntl(F_PUNCHHOLE)`、Metal 提交线程同时卡在 `IOGPUCommandQueueSubmitCommandBuffers`。即：游戏渲染期间对后备文件打洞，GPU 提交路径就被卡住；原版不挂只因为那 1 s 卡顿本身让 GPU 空闲、打洞做完才有新的 GPU 活。游戏也从不把释放过的地址再映射回来（0–1 次重叠），地址复用那条假设排除。

**第三版（现行）**：文件窗口里释放的页只 `mprotect` 成不可访问并记「待打洞」，根本不打洞、不起线程；游戏映射回来时就地清零。真机 400 s 无挂死、无 30 s 周期；6 分钟释放 1.19 GB 从未打洞，物理脚印稳定在 2.9 GB（脏页留在页缓存，内存紧时由内核按文件后备原设计换出）。`S2A_PUNCH_DEFER=0` 回原路径做负对照；后台线程那版（会挂 GPU）按评审意见删掉，不留半成品。页重新放出来的路径都要处理：0x2C、SetHeapSize 增长、栈区 MapMemory 拷贝路径（先清零再拷）、对齐路径（vm_remap 盖掉，只撤销标记）——评审在 UnmapMemory → MapMemory 这条上抓到过漏撤销标记。

**教训**：改文件后备的还页路径时，微基准之外必须进游戏跑：看开机有没有长冻结、进场景后 GPU 有没有报错，而不只看卡顿有没有消失；同一构建加 `S2A_GUEST_FILE=0` 做负对照。时序实验与结论见 #258。

## Metal 3 下计算派发的绑定会把共享编码器换掉

## 首写表的「槽号」其实是着色器内存储缓冲序号

**现象**：一款射击游戏的衍生作（#41）对话后卡到一秒一帧。实局卡顿场景里每帧绘制笔数不变（约 1370 笔），GPU 时间却一路涨：91 → 565 ms（约 180 帧内）。

**根因**：一笔间接绘制（实例数由剔除计算着色器 `029d9c3ec1fcb39f` 用原子加写出）的实例数每帧本该清零，靠的是翻译器拿出来、由宿主在派发前代做的「首个线程写入」（first_store）。反射里 first_store 的 `reg` 是着色器内存储缓冲的序号（绑定项的 `index`），宿主却当 NVN 存储槽用（`S.ssbo[5][reg]`）。这个着色器 5 个存储缓冲 index 0..4 对应槽 4/2/0/1/3，清零写到了槽 0 的别的缓冲上，实例数每帧 +40 从不归零，那一笔越画越重。

**做法**：`nvn_refl.m` 解析 first_store 时按同一份绑定表把 index 换成该项的 `reg`（NVN 槽）。修在宿主，已出的包换新宿主即生效、不用重出。回放：实例数恒为 40，那一遍 127 ms → 1.5 ms，整帧 182 → 48 ms。单测 `t_nvn_first_store` ⑥：旧实现写进槽 0、槽 4 得 out[2] = 1。翻译器 Dsh.cs 的注释「reg = 存储缓冲槽，即 index」不成立（index ≠ 槽时），以后照宿主口径读。
## 改写器读 .eh_frame 不认绝对指针编码（absptr）

**现象**（#286，程序号 01E6A672A8800000，Windows 出包）：改写阶段 `s2a-rewrite` 退 1，`改写失败：不支持 EH 编码 0`。

**根因**：CIE 没写 R 增强时，FDE 的 pc_begin 按缺省编码 0（DW_EH_PE_absptr，AArch64 上 8 字节绝对地址）存；改写器只认 udata4 / sdata4 / udata8 / sdata8。位置无关映像里这个槽是装载器按 R_AARCH64_RELATIVE 填的：lld 缺省原位留 0、加数只在 RELA 表里，GNU ld 原位也写——只按 8 字节读原位会把 lld 产的函数全当成从 0 开始。

## Apple C 改写器的暂存对覆盖叶子函数栈下区

**现象**：原创 AArch64 叶子函数在 `sp` 下保存值，经过一条 x18 改写点后从同一地址读回，得到跳板的暂存寄存器值。

**根因**：Apple ABI 给叶子函数保留 `sp` 以下 128 字节。`plain()` 在原 `sp - 16` 或 `sp - 112` 写入暂存寄存器对，和原指令的存活数据重叠。

**读数**（期望 → 实测）：Apple M1 Pro、macOS 14.8.5、基线 `2be4b3bef`，执行 7 个合成叶子函数。期望均读回 `0xbeef` → 修前 5 个重叠用例读回 `0x1234` 或 `0x5678`，2 个对照读回 `0xbeef`，修后 7/7 读回 `0xbeef`。同一测试换回基线改写器，5 个重叠用例再次失败。

**做法**：暂存帧移到原栈下区之外。需要读 `sp` 的指令用暂存寄存器取得原 `sp`，块尾恢复暂存寄存器并回放原写回量。
## runtime/src 里的苹果专用段用 `#ifndef __ANDROID__`，别用 `#ifdef __APPLE__`

## Switch 2 sdk 的服务客户端：要么整组在导入层接管，要么一个都不接

**现象**：11-09 #299 一款动作游戏（04003F40232DE000）iPad 一进 nnMain 就 SIGSEGV 地址 0（pc sdk+0x634024），5 局同点。

**根因**：nvn2.c 只在 main 导入层接管了 `nn::chat::Initialize`（回 0、不建对象）。真 Initialize 经 `detail::InitializeUserService` 建 chat:u 服务对象存进 sdk 全局 `g_UserService`，之后每个公开接口都「锁 → 取全局对象 → 读虚表」。对象没建，Initialize 后第一个 chat 接口就读空指针。原路径放不开：InitializeUserService 末尾要 `nn::chat::gsv::Initialize` + 5 次 `OpenVirtualDisplay`（GPU 服务，直连档没有，失败即 Abort），而 sdk 内部互调不经导入表、宿主接不住（loader.c 本模块有定义就绑自己）。

**现象**：

**做法**：  
split/split2 仅在当前允许集合的最高 capacity 组至少两核时按核号降序分配两个角色，否则回退系统调度（`fallback reason=highest-group-single`）；掩码读取、请求后读回、前后台恢复及外部漂移保护不变。设备实测选核与同场景性能效果仍需新包验证。

## 条件渲染不能在下一次提交开始时忘掉尚未完成的时间戳报告

**现象与读数**：11-10，Mac M5 Pro，基线 `9f7a9aa9f`。正式 `native-test-nvn_rc_pending` 用真实 Metal 共享事件阻塞 A，A 记录时间戳报告，B 随后记录条件清红；报告计数应先归零，使 B 保留初始蓝色。Metal 3 / Metal 4 各 6 项，旧实现各 1 项失败：16/16 GPU 像素全红，期望全蓝。候选两路各 6/6 通过；完成后 CPU 将计数重置为 1，条件清红仍通过。仅撤掉跨提交报告查询，两路再次各 1 项失败；原报告表检查 5/5 通过。

## 遍内自采样：第一笔自写采样整张拷快照，手机热机每帧能耗涨 5–26%
**现象**：11-09 #307（同遍自采样一律隔离）合入前实测：我方 iPhone 01007EF00011E000热状态 2 时每帧焦耳比旧路径高 +5.3% / +9.2% / +26%，帧率低 2–7%，内存多 80–220 MB；Mac 同局第 ④ 步约 8.5 次/帧、约 50 MB/帧。

**根因**：快照几乎都来自每个渲染遍的第一笔自采样绘制。此时遍还没开，或刚按「载入」打开、本遍还没画过（dirty=0），⑤ 片上读取只在 dirty=1 时尝试，于是整张拷快照。另外 g_fb_dirty 只在开遍时清零、结束遍不清：遍结束后下一遍的第一笔仍看到旧的 1，既不走片上读也不当成内存可读，同样落到 ④。

## ANativeWindow_setBuffersGeometry 后 getWidth 报告的是缓冲尺寸；native_window 没有 SCALE_FIT

**现象**：直连交换链按游戏输出尺寸出图（`ANativeWindow_setBuffersGeometry`）时，两处平台语义与直觉相反：①调过之后 `ANativeWindow_getWidth/getHeight` 报告的是缓冲尺寸，不再是窗口/view 的像素尺寸；②`native_window` 的缩放模式只有 SCALE_TO_WINDOW / SCALE_CROP / NO_SCALE_CROP，没有等比 fit——缓冲按 view frame 双轴独立拉伸。

**根因**：缓冲尺寸是生产端属性，`getWidth` 反映的是它；AOSP `system/window.h` 的缩放枚举止于 `NATIVE_WINDOW_SCALING_MODE_NO_SCALE_CROP=3`，等比只能由 SurfaceView 的 frame（布局尺寸）本身提供——SurfaceFlinger 把缓冲拉伸到 view frame，frame 宽高比 = 缓冲宽高比才不变形。

**实验数据（期望 → 真结果）**：macOS 宿主 fake-Android 桩（tests/hostvk），基线 `3eb3318`：桩按真实语义让 `setBuffersGeometry` 之后 `getWidth` 报告缓冲尺寸，窗口尺寸判定与建链尺寸记录若继续用 `getWidth` → 期望误判为窗口 resize/把缓冲尺寸当窗口像素，真结果按此桩复现；改用租约 `s2a_wsi_state`（surfaceChanged 的 frame 像素）+ 建链时记录窗口像素后 → 期望判定一致，真结果宿主测试全绿。view 布局未在宿主覆盖，真机观感列入 B 批设备验证。

**做法**：`debug.s2a.buffer_geometry=1` 时 present 按渲染目标尺寸出图并退休重建交换链（extent=目标尺寸，整幅时等比 blit 退化为 1:1）；窗口尺寸判定在开关开时读租约 frame 像素而不是 `getWidth`；Java 侧把 SurfaceView 布成缓冲同比例的居中矩形，替代 GPU 等比 blit 与黑边清屏。（尺寸目标从 crop 改成渲染目标、触摸层退回整窗是 #203 复审修正，见下条。）

**补充（同一 API）**：`setBuffersGeometry` 返回 0 不证明缓冲尺寸已改——平台可能不兑现、驱动也可能按 surface min/max 把 extent 夹到别的值。兑现与否必须用调用后的 `getWidth/getHeight` 复核再付销毁+重建代价；宿主桩模拟「返回 0 但 `getWidth` 不变」时，先销毁重建的顺序会每帧重复「销毁→重建→extent 仍不等于输出尺寸」（宿主实测 `g_geo_calls` 逐帧增长、`g_destroyed_swapchains` 不为 0）；复核失败记 `geometry_failed` 退回普通等比 blit 后，同一用例 1 次请求、0 次重建（期望 → 真结果一致）。

## macOS 自带 awk 的中文字段相等比较不可信：「同」也能判成「新」

**现象**：`tools/contrib_check.sh` 的红步与基线对照里，awk 按 `$1 == "新"` / `$1 == "同" || "超" || "缺"` 给机读行分类。在 macOS（自带 awk 20200816、UTF-8 locale）上，摘要把「与基线同红」的步误打进「新红」行，同时「未证」机读行把真新红的步也算了进去——两边都漏分。同一脚本的 `grep -c '^新	'` 计数是对的，出现「计数说新红 0 步、新红行却列了一串」的自相矛盾。

**根因**：该 awk 的字符串 `==` 在 UTF-8 locale 下走 collation 比较，排序表里没收的单字 CJK（新 / 同 / 超 / 缺这类）权重相同、互判相等；`$1 == "新"` 对字段值是任一单 CJK 字都判真。GNU awk 与 `LC_ALL=C` 下按字节比较，不复发。仓内已知同坑：`tests/refresh_test.sh` 注释「$2 == "起" 连 "止" 都判相等」。

**改法**：中文字段分类一律先按字节锚定（`grep '^新	'` / `grep -E '^(同|超|缺)	'`，与计数行同一份模式）再交 awk 只格式化；或给 awk 调用前缀 `LC_ALL=C`（`pack/shell_build.sh`、`tests/gfx_gate_group_test.sh` 的既有写法）。新写 awk 判断时别 `$n == "中文"`。

**读数**（期望 → 真结果，macOS 15、awk 20200816、`tests/contrib_unproven_test.sh` 桩造 新 3 步 / 同 3 步 / 超 1 步）：改前 ②「新红逐步写原因」实得把 7 步全列成新红、③「机读行恰好四行」未证行错分，两条断言不通；改后该测试全过（13 条断言），`contrib_incomplete` / `contrib_args` / `contrib_plan` / `gate_route_matrix` 四个相关单测同绿。反向核对：桩里真新红的 s3/s4/s6 三步不再进未证行。

## 出包目录名带 glob 元字符（[ ] 等）→ 工件 modules 静默落空

**现象**：Android 资源工件 `game-build-artifact.json` 的 `modules:[]` 空，但 APK `assets/game/modules/` 里 `main.patched.bin`/`sdk.patched.bin` 齐全；设备导入前 BootContract 拒：「artifact has no modules」。同目录下所有历史包（`[游戏名 副标题]` 开头）全部中招。

**根因**：`make_pack.write_artifact` 用 `glob.glob(os.path.join(out, 'modules', '*.patched.bin'))` 枚举模块——`glob.glob` 把整个 pattern 当模式，`out` 里的 `[游戏名 副标题]` 被解析成字符类 → 匹配一个不存在的单字符目录 → 静默返回空列表。写入前的 `write_pack` 准入检查走的是 `Path(staging).glob`（staging 在系统临时目录、无元字符）所以照过；`validate_module` 在循环体内，零匹配时一次都不执行，没有任何报错环节。

## Mac 文件后备撞 macOS 脏文件页上限：16 GB 机器游戏内长停顿（#306）

**现象**：16 GB Mac 跑 Switch 2 款，游戏内整进程停 40 / 141 / 397 秒，停顿期间磁盘每秒约 5000 次 16 KB 写、和缺页一一对应，一局写盘 31 GB。

**根因**：#41 / #68 时 Mac 按「物理内存 − 6 GB」自动开客体内存文件后备（整段窗口一个 `MAP_SHARED` 临时文件），16 GB 机器跑 9 GB 池的款一律开。macOS 对脏的文件页有上限，阈值随物理内存缩放；过了之后每首次弄脏一页都要等内核写回一页，游戏推进被限成 SSD 写速，和空闲内存多少无关。

**读数（期望 → 真结果）**：独立小程序逐页写 → 16 GB Mac 共享文件映射前 2 GB 约 1.5 µs/页，2.2 GB 后 25–29 µs/页一直保持（16 KB ÷ 26 µs ≈ SSD 写速）；同机匿名内存 0.7 µs/页；128 GB Mac 写 8 GB 文件映射无拐点（2.3–2.9 µs/页）。

**做法**：Mac 缺省匿名内存，系统按需压缩 / 换出；池本身大于「物理内存 − 6144 MB」时第一局就开文件后备（8 GB 机器，PR #353）；否则只在本机本款上一局到过系统内存压力「严重」档（libdispatch 内存压力源）时开文件后备，记录在 `wire/<程序号>/mem_pressure`（`s2a_guest_file_wanted_mac`）。iOS 判定不变（单进程上限必须开）。

试过保住文件后备只换映射方式（`MAP_NOCACHE`、`F_NOCACHE`、`MADV_RANDOM`），都去不掉拐点，`sysctl` 也没有可调的脏页阈值（#353 实测）。

**以后**：别用整段 `MAP_SHARED` 文件当「省内存」手段，它不是换页，是强制写回；iOS 上同一阈值照样限速，长期要只把文件当溢出用。

**实验数据**（服务层单测，期望按语言码 = ASCII 小端手算："ja" = 0x616A、"en-US" = 0x53552D6E65）：

| 项 | 期望 → 真结果 |
|---|---|
| 位为 0、系统日语、没显式指定 | 0x53552D6E65 → 0x53552D6E65（#401 的行为不变） |
| 位为 0、显式指定日语 | 0x616A → 0x616A；把显式分支关掉 → 0x53552D6E65（红） |

**做法**：宿主把「系统语言是不是显式指定的」交给 `S2AHooks.ExplicitSystemLanguage`（`S2A_SYSTEM_LANGUAGE` 非空，env.txt 也算）；位为 0 时显式指定就回它，否则仍回美式英语。没有在真实游戏上跑过修后的宿主。
## 无人引用的共享贴图只在池 Finalize / 被别的贴图接管时放：长局低区耗尽闪退（#357）

**现象**：iPad 上一款 SRPG 长局后闪退，崩溃时低区账「拦不到的（Metal 内部）」从 1.7 GB 涨到 3.2 GB，共享贴图 463 张里 393 张已无人引用（v0.2.2）。

**根因**：共享表（同存储同描述的贴图共用一张宿主贴图）里的贴图，只在两种时候放：池 Finalize（`nvn_be_alias_drop_pool`）、别的描述的贴图接管同一段存储（`alias_take_over`）。游戏 Finalize 掉贴图、存储在池里留着不再用时，宿主贴图永远留着。Mac 同款局：无人引用的平均 3.9 MB 一张，91% 被 GPU 写过，切场景时 51 → 121 张。

**做法（按 NVN 语义推，不按款开关）**：贴图对象只是描述，字节在存储里；对象全 Finalize 后同存储同描述重建仍读到原字节。所以：没被 GPU 写过的（内容就是存储里的，重建时取回）闲 `ALIAS_IDLE` 次提交后即放；GPU 写过的（内容只在宿主贴图里）等它写过的块全被改写再放，判据用现成的写账本（`gpw_stale`：每个 GPU 写过的 GOB 记了当时内存字节的哈希，任何写入方改过就对不上）；低区账本要地址时（`s2a_lowva` 腾退回调）按最久没用先放 GPU 写过的，重建时那些块读 0，与其它贴图建在 GPU 写过的存储上的现有规则（`gpw_zero_rect`）一致。显示 / 视频解码贴图不碰。每 300 帧随内存读数跑一遍（`alias_orphan_pass`）。

**读数（期望 → 真结果）**：单测 `t_nvn_alias_orphan`（Metal 4 / 3）：没写过的放 +1 → +1；写过、存储没动两遍都留 → 留；只改 4 KB → 留；整段改写 → 放 +1；账本要地址 → 放 +1；活对象 → 留。9 项全过，`t_nvn_alias_overwrite` 7 项、`t_nvn_pool_tex` 16 项照旧全过。Mac 同款 16504 帧长局（只有前两条，阀门那条之前）：没写过的放 15 张 21 MB，存储被 CPU 写的 0 张——这款 GPU 写过的孤儿存储不被改写，只能靠阀门。

**以后**：「只在某个事件时放」的缓存先问内容还会怎样作废、地址不够时谁让路；判「存储被改写」先用写账本，别另做页保护（第一版用页保护，只认 CPU 写、还漏共用半页）。单测进程没有宿主的信号处理器，写被保护的页要自己装一个转给 `s2a_direct_fault`。
## NVN 视图的目标与层数 Metal 建不出时，Metal 断言直接结束进程（#199）

**现象**：一款足球游戏三个版本都在进游戏后同一处闪退，同一支着色器、同一个纹理槽，Metal 断言 `newSliceRange.length(1) must be a multiple of (6)`，栈 `tex_by_id → pool_tex_obj → pool_tex_update → pool_gpu → encode_args → draw`。

**根因**：游戏的纹理视图把目标设成立方体，底下是只有 1 层的 2D 贴图；`tex_by_id` 按视图目标与层数直接调 `newTextureViewWithPixelFormat:textureType:levels:slices:`。Metal 对视图类型与层数的组合有硬规则（立方体正好 6 层、立方体数组 6 的倍数且底下是分层贴图、3D 只能对 3D、层范围不越界），不合法时不是返回 nil，而是断言结束进程。

**读数（期望 → 真结果）**：单测 `t_nvn_view_fit`（Metal 4 / 3）：1 层 2D + 立方体视图空槽、合法立方体视图照旧建、越过末层空槽、2D + 3D 空槽、无视图原样，5 项全过；同一单测编修复前源码 → 进程在 ① 处被同一句 Metal 断言结束（Abort trap 6）。

**做法**：建视图前按 Metal 的规则核一遍，不合法就报一次红、按空槽处理（读 0），同 Ryujinx 对目标维度对不上的视图不绑（`Texture.GetTargetTexture` 返回 null），也同本函数里压缩格式按非压缩看、mip 越界两处现有的处理。

**以后**：调 Metal 的建对象 API 前，参数组合要先按它的硬规则核过；Metal 的参数校验失败是断言，不是返回 nil，别指望事后判空。
## 纹理池里「没被写过的渲染目标读 0」只看对象自己的序号：同存储另建的采样对象一直读 0

**现象**：代码层复现（两款 iPad 3D 全黑排查中发现，那两款的真因未确认）：游戏用对象 A 当渲染目标画，再在同一段存储、同样描述（只差 COMPRESSIBLE 等用途标志）上另建对象 B 登记进纹理池给着色器采，B 一直读到占位（全 0）。

## GameChat「没在聊」把摄像头视频存储也回成 0：游戏开机就建图像池、拿句柄 0 建原生图像后中止（#116）

## iOS 远端影子按 2 MiB 分块、跨两次映射的内存池影子不连续：图形后端建不了零拷贝缓冲就 FATAL（#450）

**现象**：iPhone 上一款第一方 RPG 每次首帧前中止：`FATAL memory pool 0x80549cc000..0x80586cc000: its far shadow is not contiguous at 0x8058600000, cannot build one zero-copy buffer`，直连安全网连续 3 次「首帧前崩溃」。

**根因**：远端别名区的游戏地址在宿主没有地址，内容放在影子里（runtime/src/far.c）。iOS 地址紧，影子从堆区顶往下按 2 MiB 切，每次映射请求内部连续；游戏按地址递增分两次映射、再在这段上建一个内存池时，后一次的影子落在前一次下面，池的影子在 2 MiB 边界断开。图形后端 `pool_host` 要求整池一段宿主内存（一个零拷贝 MTLBuffer），遇到就 MDIE。Mac 有 #419 的线性影子（整个远端一次预留），不会遇到。

**做法**：影子不连续时，预留一段连续宿主地址，把各块影子页按游戏顺序 `vm_remap` 进来（不拷贝、同一批物理页，CPU / GPU / 远端缺页代执行看到的是同一份内存），缓冲建在这段视图上，视图随缓冲的 deallocator 释放。`up_tex_src` 与帧录不再各自调 `pool_host`，改用池已存的宿主地址（不另建视图）。

**读数（期望 → 真结果）**：单测 `t_nvn_far_pool`（生产 far.c，`S2A_FAR_LINEAR=0` 同 iOS 分块，按地址递增两次映射）：池建得出、视图与两块影子双向同一份、GPU 经池缓冲读到第 2 块影子的字节、一次映射的池照旧直接用影子 → Metal 4 / 3 各 4 项全过；同一单测编修复前源码 → 同一句 FATAL、Abort trap 6。

**以后**：「一段游戏内存 = 一段宿主内存」的假设在远端别名区不成立；要整段宿主地址的地方用视图拼，别靠分配器「多半相邻」。

## 桌面 GL 上下文报 4.5，却缺 4.5 以下的入口：LÖVE 引擎拿到空指针就调，iOS 上表现为 CODESIGNING 0x2 闪退（Balatro）

**现象**：玩家 iPhone 上 Balatro 启动即闪退，MetricKit 两次一致：`CODESIGNING Code 0x2`、signal 9、归因线程根帧地址 0（不在任何映射区）。宿主日志最后几行是 `glGetIntegerv(0x9126 / 0x8073 / 0x88ff)`、`glGetFloatv(0xb12)` 没实现，之后没有别的记录。

**根因**：在 iOS 上跳到地址 0 就会以 CODESIGNING 0x2 被结束，不是签名问题。Balatro 用 LÖVE 11 引擎，它按 `GL_VERSION`（本层桌面上下文报 `4.5.0`）用加载器取全部入口，再按版本走对应路径。按 LÖVE 11.5 源码 `OpenGL::setupContext`，先跑 `initMaxValues()`（最后一笔正是 `glGetFloatv(GL_POINT_SIZE_RANGE)` = 0xb12），紧接着调 `glVertexAttrib4fv`。本层只有 `glVertexAttrib1f`，查表回空，于是调到 0。

- `glBufferStorage`（4.4 以上建流式缓冲），以及持久映射 `glMapBufferRange(PERSISTENT | COHERENT)`。原来这两个位直接报 INVALID_VALUE、回空指针，画在映射着的缓冲上也会被拒。
- `glDrawElementsBaseVertex`（画四边形批）、`glGetUniformfv`（建着色器后读回初值）、`glClearBufferfv`（清画布）、`glInvalidateFramebuffer`（切画布）、`glPointSize`、`glUniform*uiv`、非方阵矩阵。

**做法**：补齐以上入口，按 GL 4.5 规范实现。几个要点：
- 不可变存储：之后不许 BufferData，没有 DYNAMIC_STORAGE 不许 SubData。
- 持久映射：只对带同样标志的不可变存储；映射期间不换存储，允许在映射着的缓冲上画。
- 6 个查询按规范和 Metal 上限给值：SAMPLE_BUFFERS / SAMPLES 按当前帧缓冲、CONTEXT_PROFILE_MASK = core、MAX_3D_TEXTURE_SIZE / MAX_ARRAY_TEXTURE_LAYERS = 2048、POINT_SIZE_RANGE = [1, 511]。

**读数（期望 → 真结果）**：`t_gl_api` R 组（桌面上下文按 LÖVE 的调用顺序，真 Metal、GPU 读回）：
- 查询值、`glVertexAttrib4f` 设的颜色、持久映射着画两段（左红右绿）、基准顶点画第二段、`glClearBufferfv` 不改清除值、`glGetUniformfv` 读回 → 14 / 14 过。
- 同一单测用补齐前的 GL 源码（`GL_API_SRC`）→ R 组第一项「取不到 glVertexAttrib4fv」红。
- 没有 Balatro 原件，真游戏首帧没有本机证据，要玩家复测。

**以后**：版本串决定游戏走哪条路径，报哪个版本就要有那个版本游戏会调的入口。普查「lookup → 没有（回空）」时，按引擎源码对出它真会调的那些先补。

## 安卓直连 compute 每笔 dispatch 重建 VkPipeline：驱动每笔重跑 LLVM 编译，单核吃满

**现象**：8E（骁龙 8 Elite）simpleperf 显示一条 `nx-*` 线程长期吃满一核，58% 样本在 `nvn_vk_compute_pipeline_build → vkCreateComputePipelines` 里，热点全是 `/vendor/lib64/libllvm-qgl.so`（高通着色器编译器）+ scudo 分配。

**根因**：`android/native/nvn/nvn_vk_compute.c` 每次 dispatch 都 `vkCreateShaderModule` + `vkCreateDescriptorSetLayout` + `vkCreatePipelineLayout` + `vkCreateComputePipelines(VK_NULL_HANDLE)`，用完在 owner 销毁里连对象一起销毁——SPIR-V 查找有缓存，但 VkPipeline 每笔重建，驱动对每次创建重跑后端编译。iOS 侧同类管线挂在着色器对象上只建一次。

**做法**：进程内 PSO 缓存（`debug.s2a.compute_pso_cache=1`，默认关做 A/B）：键 = SPIR-V 字节 + 描述符布局签名（set/binding/kind 序列）+ 特化常量记号，hash 快筛 + 全字节比对；值 = module + set layouts + pipeline layout + pipeline；有界 LRU（64 项，表引用 + 在途 owner 引用计数，逐出只动 refs==1 项，满表全在途退回按笔创建）；descriptor pool/set 与影子缓冲仍按笔 owner 管（带每笔数据）；同设备一份 VkPipelineCache；session 在 device_destroy 前 `nvn_vk_compute_pso_cache_release` 整表释放（另带设备句柄切换惰性冲表）。`nvn_vk_compute_cpso_totals` 永不清零地累计创建次数/耗时，逐帧 TSV cpso_n/cpso_us 列差分取数（弱符号，源不在整列不出）。

**读数（期望 → 真结果）**：宿主替身 `w2_compute_pipeline_test`：门关 3 次 dispatch = 3 次 `vkCreateComputePipelines`（修前行为）→ 门开同 shader = 1 次；负控 SPIR-V 不同/布局签名不同各 = 2 次；LRU 70 键入表 64 项；`negative_pso_never_hit` 变异恰红在 pipe_calls==1 断言 → 77 用例 + 16 失败点 + 28 变异全过。设备读数待 8E A/B（开关双态，同一局 TSV 里看 cpso_n 从每帧 N 降到 0）。

**以后**：凡是在「每笔命令路径」上建 Vulkan 对象的地方都要问一句能不能按身份复用——创建类调用在高通栈上是编译器入口，不是簿记开销。

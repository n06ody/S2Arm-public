# 坑记录

从这里开始记录，每条写现象、根因、改法。

## GL 直连预检与翻译器的工具选择不一致（issue #269）

**现象**：`GLSLANG` 指向可执行工具、PATH 没有 `glslangValidator` 时，纯 GL 提前报缺工具，混合 GL 跳过离线库；这不证明 issue 报告者的失败属于同一原因。

**根因**：`direct_lib.sh` 检查 PATH 上固定名称，`gl_shaders.py` 则使用 `GLSLANG`（仅未设置时回退固定名称）。

**读数（期望 → 真结果）**：Linux 容器、基线 `31bfb8d`，合成工具和隔离 PATH，纯 GL 入口与混合 GL 分支各测 9 种情况，共 18 项；空格路径的显式工具应被调用 → 修前两分支均未调用、修后均调用；回退生产检查后两分支再次未调用。未设置变量时的 PATH 回退、无效或空变量和缺 `spirv-cross` 同测。未跑真实 Windows、Mac 出包或游戏复测。

**做法**：两处分支按翻译器相同的变量选择检查可执行文件；保留缺工具时各自的失败方式。

## Mac 手柄输入停在 120Hz 定时器网格上

**现象**：Mac 上蓝牙 DualShock 4 的按键 / 摇杆从系统事件到前端发布均值 4.21ms、中位 4.29ms、P99 8.36ms、最大 8.92ms，分布落在 1/120 秒（8.33ms）的网格上；同机键盘走 keyDown 事件路径，中位 0.56ms。

**根因**：`macos/front_mac.m` 只在 1/120 秒的 NSTimer 里调用 `poll_input()` → `sample_input()`，`GCExtendedGamepad` 没有接 `valueChangedHandler`；iOS 侧已用事件回调（`ios/controller.m`）。

**实验数据（期望 → 真结果）**：Apple Silicon Mac（Mac17,3，macOS 26.7.1）、蓝牙 DualShock 4、游戏《怒首领蜂大往生 临回转生》59.96 fps。手柄前端 420 条状态变化：均值 4.21ms / 中位 4.29ms / P99 8.36ms / 最大 8.92ms → 改为 `handlerQueue = main` + `valueChangedHandler` 后回调直接 `sample_input()`，不再有定时器量化；单测验证回调发布整份当前状态，长按跨回调和 120Hz 回退采样仍保持。

**做法**：`install_pad_handler()` 给每个 `GCExtendedGamepad` 装 `valueChangedHandler`，回调里 `sample_input()`；120Hz 定时器保留给键盘 / 鼠标粘键核对并补装新连接的手柄。

## 覆盖更新中断后重试删除唯一旧版备份

**现象**：安装目录已改名为 `.s2arm-old`、新版还没改名到安装位置时中断，再次执行 `apply()` 会删除旧版备份，随后因安装目录不存在而失败。

**根因**：更新入口无条件清掉已有备份，再调用要求安装目录存在的 `swap()`，没有恢复两次改名之间的中断状态。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`；用合成目录构造第一次改名后的落盘状态。重试成功安装新版 → 改前失败且旧版消失、改后成功；新版暂存目录丢失时保留并重启旧版 → 改前旧版消失、改后恢复旧版；恢复改名被拒时原备份保留 → 改前消失、改后保留。`ApplyTests`、`RunnerTests`、`Ed25519Tests`、`VersionTests` 共 15 项通过。临时副本换回基线 `updater.py` 后，两项点名回归重新失败。

**做法**：安装目录缺失而旧版备份存在时先恢复旧版，再走正常替换。未执行真实安装包更新、断电或 Windows 文件占用验收；该验证仅覆盖两次改名之间的中断状态。

## 清理中间产物时沿链接删除存档目标

**现象**：`iPhone/<程序号>/intermediate` 是指向同库 `saves/<程序号>` 的目录链接时，`prune_build()` 删除存档目标，链接本身却留下。

**根因**：`library._rm()` 先经 `contained()` 解析链接，再检查 `is_symlink()`；目标仍在游戏库内就通过了包含检查。父目录是链接时也会删除它指向的文件。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`，均为临时目录与合成字节。自动清理后存档保留 → 改前文件消失、改后内容原样保留；显式清理、库外目标、文件链接和悬空链接同测。`test_cleanup_links`、`test_free_space`、`test_saves` 共 63 项：62 项通过、1 项 Windows junction 用例因宿主不符跳过。临时副本换回基线 `library.py` 后，两项点名回归重新失败。

**做法**：先核对未解析的路径是否属于清理根，拒绝经过父目录链接；叶子链接只删除链接本身，Windows junction 使用 `rmdir`。未做 Windows 真机验证，也不据此宣称能消除并发路径替换的所有竞态。

## 发版 Mac App 出包失败：shader_extract_failed（issue #8）

**现象**：  
发版 Mac App（如 v0.1.0），游戏 RomFS 要解码器（Oodle LZ5）或运行时 GLSLC 时，出包报 `shader_extract_failed`，阶段停在「分析画面」。

**根因**：  
- `pack/stage_extract.sh:63` 调 `tools/host_build.sh` 现场 make 编 Mac 宿主（含 C#，S2A_CS=1）
- 发版 App 只带 Runtime（`pack/jobs/core.py:500` 设 `DOTNET_ROOT=Runtime/dotnet`），无 SDK
- make 的某步调 `dotnet --version`，Runtime-only dotnet 报「No .NET SDKs were found」退非 0
- 失败被 `stage_extract.sh:63` 归因：「【红】t<游戏 ID> 编译 Mac 宿主失败（The command could not be loaded...）」
- 上层按阶段 `sh_extract` 映射错误码 `shader_extract_failed`

**实验数据**：  
- 设备：Mac（发版 App v0.1.0，S2ABuildID=7aff9afa-86be9c95）
- 数据目录：<本机复现用的临时数据目录>
- 游戏：010021C000B6A000 以撒重生+ v1.7（中文忏悔本，含 Oodle LZ5 → decoder_need 为真 → S2A_CS=1）
- 期望：ipa completed
- 真结果：rc=1，analyze 2/10（26 秒），错误码 `shader_extract_failed`
- 日志证据：
  - `Runtime/dotnet/dotnet --version` 输出「No .NET SDKs were found」
  - `refresh.log` 第 8 行「【红】t010021c000b6a000 编译 Mac 宿主失败（The command could not be loaded...）」
- 负对照：暗黑3（不需解码器）未复现，task completed 346 秒

**做法**（提交 45d5ffe，分支 fix/packaged-mac-host）：  
1. **打包时已放宿主**：`launchers/macos/bundle_engine.py:179` 已有 `shutil.copytree(host, destination / "Binaries/S2ArmGame.app")`，打包时把编好的宿主（S2A_CS=1，含 C#）放进引擎 Binaries/ 目录
2. **检测并设环境变量**：`pack/jobs/core.py` 的 `Context.env` 方法，在发版环境（runtimeSchema 3/4）中：
   ```python
   from embedded import artifact
   try:
       bundled_host = artifact(self, "S2ArmGame.app")
       if bundled_host and (bundled_host / "Contents/MacOS/s2arm-host").is_file() and (bundled_host / "Contents/MacOS/libs2a_vaguard.dylib").is_file():
           env["S2A_BUNDLED_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
           env["DM_GLSLC_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
   except Exception:
       pass   # 源码树开发：没有内置宿主
   ```
3. **跳过现场编译**：`pack/stage_extract.sh:51-64` 在需要宿主时，检测 `S2A_BUNDLED_HOST`：
   - 如果设置且文件存在 → 输出「[s2a] 使用发版 App 内置 Mac 宿主：$S2A_BUNDLED_HOST」，跳过 `host_build.sh`
   - 否则 → 按原逻辑现场编译（源码树开发构建）
4. **单测覆盖**：`tests/stage_extract_test.sh` 添加用例「有内置宿主 → 不编宿主、跳过 host_build」

**射程**：  
- ✅ 所有发版 Mac App，游戏需要解码器（Oodle LZ5）或运行时 GLSLC
- ✅ 调用链：oneclick → refresh → stage_extract → extract.sh / glslc_offline.py（DM_GLSLC_HOST 环境变量传递）
- ✅ 源码树开发构建不变（runtimeSchema != 3/4 或 artifact 返回 None 时走原路径）
- ✅ Windows 不受影响（pack/orch/oneclick_win.py，不走 Mac stage_extract）
- ⚠️ 边界：如果打包流程被修改，未把宿主放进 Binaries/，会退回现场编译（因 artifact 返回 None，与源码树开发相同）

**验证**：  
- 单测：`bash tests/stage_extract_test.sh` 全通（23 个 Python unittest + 40+ 个 shell 断言）
- 现有 App：`/Applications/S2Arm.app/Contents/Resources/Engine/Binaries/S2ArmGame.app/` 存在，包含 s2arm-host (106M，含 C#) 和 libs2a_vaguard.dylib (67K)
- 完整打包 + 游戏测试未执行（耗时 15-30 分钟，当前负载 10+）

## 命令行出完包，Mac 前端认不到（装机 / 推资源包报 container_stale）

**现象**：用 `pack/oneclick/oneclick.sh` 命令行出好的 IPA 与资源包都在 `<游戏库>/iPhone/<程序号>/` 下，Mac 前端却说这款没有 iPhone 版；点「装到 iPhone」或推资源包报 `container_stale`。

**根因**：启动器判「这款的产物是不是按本壳出的」看 `<输出>/shell.id`（`pack/jobs/ipa.py` 的 `SHELL_STAMP`，`ipa.current_root()` 只有它对得上当前壳编号才认这份产物）。这份戳只有**启动器自己的打包任务**会写，命令行一键出包（`oneclick.sh` → `ipa.sh` → `ipa_tail.py`）不写，于是产物齐全但前端判「没出过」。

**改法**：`ipa.sh` 出包成功时把壳编号（`<壳目录>/manifest.json` 的 `details.shellId`）写进产物根 `.shell_id` 并随 `root_commit` 提交；`oneclick.sh` 出包成功后把它转交成 `<输出>/shell.id`（与启动器写同一份、同一口径）。

**读数**（期望 → 真结果）：命令行重出这款后 `<输出>/shell.id` → 期望 `e2c369640047cade`，真结果 `e2c369640047cade`；用引擎自己的 `install.latest_ipa()` / `ipa.current_root()` 复核 → 期望返回 IPA 与现行产物根，真结果都返回了（改前 `current_root` 返回 None）。

## 出包停在「出包 2/5」、错误码只有 package_failed「原因没认出来」

**现象**：iPhone 出包到 `出包 2/5` 后工具退出，错误摘要写「Packaging incomplete / We couldn't recognize the cause」（9.78 GB 的 PERSONA4 The GOLDEN，0.1.0，iOS 目标 iPhone 17 Pro）。`pack/ipa.sh` 的 `PN=5` 是 ①组装 ②签名 ③打 ipa ④资源包 ⑤资源包核对；进度只到 2，说明停在 ③「打 ipa」（`pack/ipa_tail.py` 的 `write_ipa` 步）——其余步要么有自己的日志（build.log / sign.log / pack.log / verify.log），要么在 `pack/jobs/ipa.py` 的 `PACKAGE_FAILURE_PREFIXES` 里能映射。

**根因**：③ 这一步有两处把原因丢掉。一是 `ipa_tail.assemble` 调 `step()` 时没给日志，输出落进 `$W/pkg/tail.out`，而 `ipa.sh` 失败时只把 `build.log` 拷进 `S2A_ROOTS/.failed/`、随后 `root_abort` 删掉整个临时产物根，于是真正的原因（体积账 / errno / zipfile 异常）既没进红行也没进摘要；`PACKAGE_FAILURE_PREFIXES` 也没有「打 ipa」这一项，归因只能落到 `package_failed`。二是同一类「原因看不见」的口子：`app_bundle.write_ipa` 按设计不写 zip64（侧载工具读不了），而 32 位上限只有「单文件」一道闸，条目数 / 整份字节超了由 `zipfile` 在写条目或收尾时抛 `LargeZipFile`；它不是 `OSError`，`main()` 的 `except (OSError, ValueError, RuntimeError)` 也接不住，于是变成裸 traceback，父进程只拿到退出码。**这单具体是撞了哪条上限、还是别的 errno，以修复后红行里的原文为准**（IPA 不一定到 2 GiB，先不认定）。

**改法**：③ 有独立日志 `pkg/archive.log`，失败时把最后一行（红行优先）写进红行与错误摘要，`ipa.sh` 失败时也把这份日志留到 `S2A_ROOTS/.failed/`；`write_ipa` 归档前先算体积账（条目数 / 单文件上限能提前判死，整份取决于压缩后大小），收尾的 `LargeZipFile` 转成带体积账的 `BundleError`，`main()` 再兜一层，任何一条路都不落裸 traceback。

**读数**（期望 → 真结果）：归因 `打 ipa 失败（OSError: [Errno 28] No space left on device）` → 期望 `disk_full`，改前 `package_failed`、改后 `disk_full`（`pack/jobs/errors.classify_failure`，合成输入）；`tests/app_bundle_test.py` 新增三条体积账用例 → 改前 2 条 ERROR、改后全绿（34 条，skip 2）；`tests/ipa_tail_test.py` 新增 `archive_reason` 用例 → 改前 AttributeError、改后全绿（7 条）。

## 帧率上限非整除档：生产端交换间隔下限不能四舍五入

**现象**：通用层 `FramePacingPolicy.SwapIntervalFloor` 原来是 `round(vsync / 上限)`，只认 0/30/60/120 时都整除，结果对。放开到任意档后，上限 40 得 `round(1.5) = 2`，也就是生产端每 2 拍出一帧（30 帧），比用户给的上限 40 还慢。

**根因**：交换间隔 k 在 60 Hz 节拍下给 60/k 帧，要「不慢于上限」应取满足 60/k ≥ 上限 的最大 k，即 `floor(vsync / 上限)`（至少 1）。四舍五入在 1.5 这类半值上往上取，就落到了更慢的一档。

**读数**（期望 → 真结果）：`tests/frame_pacing`「40 FPS floor is 1」改前（round）expected 1, got 2，改后（floor）通过；30 / 60 / 120 的下限两种算法同为 2 / 1 / 1，原有断言不变。

**做法**：下限按 `floor` 取，并用非整除的档（40、24）做断言。上限本身仍由呈现端 `MinimumPresentationInterval` 的 1/上限 保证。

## Windows 玩家出 CRI 压缩的游戏：抽取报 WinError 2（issue #95）

**现象**：PERSONA4 The GOLDEN，v0.1.3，Windows 11，「抽取 + 直连库」阶段失败，`direct_lib.log` 只有 `concurrent/futures/_base.py line 401` 和 `FileNotFoundError: [WinError 2]`，后面不带路径。

**根因**：`nxsh_extract._cri_lib` 遇到 CRILAYLA 数据时在子进程池里现场调 `clang` 编 `crilayla.c`。Windows 发版预编了 dsx 和 Yaz0 小库，漏了这一个；玩家机器没有 clang。构建机装了 LLVM，所以 11-05、11-06 的女神异闻录5 都没暴露。Windows 上起子进程失败的 `WinError 2` 不带文件名，打开文件失败是 `Errno 2`，可以据此区分。

**改法**：`bundle_prepare_win.py` 把库编进 `Binaries/Prepare/codecs`，文件名带源码摘要；`_cri_lib` 先用预编件；`oneclick_win --check` 缺这份预编件时起单前就报红。

**读数**（期望 → 真结果，Windows 11，PATH 去掉 clang，真实入口 `nxsh_extract.py`，手造含 CRILAYLA 的 CPK，1 支着色器）：旧代码 → 期望 WinError 2，真结果 rc=1、同样的 `_base.py line 401` + `WinError 2`；新代码无预编件 → 期望 WinError 2，真结果相同；新代码有预编件 → 期望键 `503475149b866d8c`，真结果 rc=0、解开 CRILAYLA 1 段、键相同。

## Windows：机器设了 LANG=C / en_US，中文路径被 cygpath 截断（issue #85）

**现象**：Windows 出包在「抽取 + 直连库」1 秒内失败。安装在中文目录时报 `can't open file 'D:\translator\spvc_inproc.py'`（摘要里是 `D:[PRIVATE_PATH len=26 depth=2]`），装到英文目录后报 `D:/ 缺 romfs/ 或 exefs/main`。

**根因**：`direct_lib.sh` 用 `cygpath -m` 转路径。MSYS 的 `cygpath` 在 `LANG` / `LC_ALL` 为非 UTF-8 值时，输出在第一个非 ASCII 字符处截断；作业环境继承了机器上的语言变量。脱敏器统计 `len` 时不含盘符，且把双反斜杠算一个，看长度要按这个口径算。

**改法**：`win_runtime_env` 和 `s2arm_env.cmd` 设 `LC_ALL=C.UTF-8`，所有 Windows 出包作业生效。

**读数**（期望 → 真结果，Windows 11，Git Bash `cygpath`，真实 `direct_lib.sh`，产物根在 `游戏库` 下）：`LANG=C`、`LANG=en_US`、`LC_ALL=C`、`LC_ALL=POSIX` 下 `cygpath -m` → 期望截断，真结果 `C:/Users/example/v85/`；`LANG=C` 跑旧环境 → 期望与玩家同形，真结果 `C:/Users/example/v85/ 缺 romfs/ 或 exefs/main`；`LANG=C` 和 `LC_ALL=C` 跑新环境 → 期望过这一检查，真结果过了第 61 行（后面失败是精简目录缺 `tools/progress.sh`）。

## Windows：任务记录原子替换撞上读方，长任务整局失败（issue #130）

**现象**：Windows 长任务报 `journal_write_failed`（拒绝访问），事件日志写入正常，磁盘和权限都没问题。

**根因**：`atomic()` 用 `os.replace` 替换任务记录。Windows 上目标文件被打开且没带 `FILE_SHARE_DELETE` 时，替换抛 `PermissionError`；Python 的 `open()` 不带这个共享标志，一次撞上就让整局失败。

**改法**：Windows 上 `PermissionError` 退避重试 6 次（共约 1.6 秒），其余平台不重试。

**读数**（期望 → 真结果，Windows 11，Python 打开目标文件 0.3 秒）：旧 `atomic()` → 期望 `PermissionError`，真结果 `[WinError 5] 拒绝访问`；新 `atomic()` → 期望写入成功，真结果成功，用时 0.38 秒。

## Windows Metal：环境检查与编译使用不同安装目录（issue #120）

**现象**：Metal 工具在非默认目录且已加入 PATH，启动器版本检查能找到，`oneclick_win --check` 仍报缺；绕过预检后，编译包装仍从 C 盘默认目录取工具。另有 `S2A_METAL_BIN` 时，版本检查会先选 PATH 上另一份。

**根因**：`winenv.NativeProbe` 查询 PATH，`oneclick_win.metal_bin()` 只认显式目录或默认目录；实际 Python / C# 编译包装只读 `S2A_METAL_BIN`，没有收到预检选中的目录。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.14.6、基线 `517d39e`，仅用中文空格临时目录和原创合成工具。新增 10 项回归：回退两份生产文件后应红 → 6 项失败（含 1 项子进程错误）；修复后应绿 → 10/10 通过。真实启动子进程分别验证 PATH 安装、显式目录覆盖及 Mac 不注入 Windows 目录；PATH 前面另放一份链接器，实际仍执行选中安装的两个工具。未运行 Windows 原生工具、Apple 编译器或完整游戏出包，此读数只证明目录选择和子进程传递。

**做法**：预检与默认版本探测共用 `metal_exe()`，按显式目录 → PATH → 官方默认目录选择；相对 PATH 先固定为绝对路径。出直连库时将选中目录传为子进程的 `S2A_METAL_BIN`，让编译器与链接器从同一安装取用；显式目录缺失时保留报缺。

## VP9 托管解码器的去块滤波几乎不生效（#44）

**现象**：P4G 片头经 Nvdec（Ryujinx 托管 VP9 解码器）解出的画面与 libvpx 不同，从第一帧开环路滤波（滤波级别 5）的帧起每帧都不同，方块边更明显；运动向量与计数逐字节相同，只有像素不同。

**实验数据（期望 → 真结果）**：Mac arm64，手机上抓的 P4G 片头 1033 个 NVDEC 作业（movie 37）喂托管解码器，比显示帧 Y 平面 FNV-1a 与 libvpx 1.17.0 直接解 IVF 的结果：修前 → 期望全同，真结果 3/838 相同（不同的从第一帧开滤波的作业起）；main 未带 #86 → 同样 3/838；修后 → 838/838 相同。手机上 #86 构建抓到的 C# 输出与 Mac 重放逐作业相同（1033/1033），不是线程竞争。`tests/vp9_loop_filter_init`：8 档锐度 × 64 级 × 16 字节与 libvpx 公式一致（24576 项）；负对照：删掉 `Decoder.Decode` 里的调用 → 接线检查报红；清空 `hev_thr` 填充 → 6144 项报红。

**做法**：`LoopFilter.LoopFilterInit` 按 libvpx 填阈值，`Decoder.Decode` 设好滤波字段后、`LoopFilterFrameInit` 之前每帧调一次（每帧 64 级 × 16 字节，开销可忽略）。走整段码流的 `DecodeFrame` 路径（S2Arm 不用）没改。

**根因**：`android/native/direct/compile_export.c` 每次发布先在请求目录里 `openat(".lock", O_CREAT)` 再加锁。目录刚建好时，多个进程同时 O_CREAT 同一个文件，macOS 的 APFS 偶发对其中一个返回 ENOENT。安卓（ext4 / f2fs）上没有这个问题，但门禁在 Mac 上测。

**读数**（11-09，本机 Apple M5 Max）：最小复现程序 12 进程并发 O_CREAT，480 次出现 4 次 ENOENT；原实现单测 40 路并发 ×3 轮 11/120 红；改为对目录描述符加 `flock` 后 40 路 ×5 轮 200/200 过，负对照照旧报错。

**做法**：跨进程互斥直接锁目录本身（`flock(dirfd)`，Linux / 安卓 / macOS 都支持），不要靠「大家都去创建同一个锁文件」。

## Mac 窗口比例和模拟手机屏不一致时，宽屏内容判据整段不跑

## 线性贴图建不了零拷贝视图时，内容进不了 GPU

**现象**：哈迪斯 II iPhone（iOS 18 / Metal 3）主菜单整屏发绿（#255）；上古卷轴5 A19 Metal 断言 `bytesPerRow 3840 < 5120` 后 abort（#262）。

**根因**：`nvn_mtl.m tex_linear` 把线性贴图直接建成池缓冲上的零拷贝视图。iPhone 要求偏移 / 行距按 64 字节对齐（Mac 宽），哈迪斯一张 8x8 BGRA 调色贴图行距 32，对不齐就退成私有贴图、只在建时从存储填一次，之后 CPU 写的全看不到；而退到打包上传时 `nvn_deswizzle` 对线性排布直接返回 -1（日志「deswizzle failed format 0x9a」），内容一字节没传。行距放不下一行 Metal 像素时又不核就建视图，触发 Metal 断言。

**做法**：去混排认线性排布（按行距逐行拷，行距不够一行返回失败）；建不了零拷贝视图的线性贴图（线性渲染目标除外）在 `tex_mtl_` 并进 CPU 写过的贴图那条路（上传 + 脏页重传）；`tex_linear` 建视图前核行距。Mac 上用 `DM_NVN_LINEAR_ALIGN=64` 模拟 iPhone 对齐、`DM_NVN_LINEAR_UPLOAD=0` 退回旧行为做对照：主菜单平均饱和度 旧 21.3 → 修后 166.4（正常局 166.5）。

## 装 NRO 补绑导入时，槽已被游戏设成只读

**现象**：玩家 iPhone 17 Pro Max（iOS 27.3）上 01001BA027DD8000 起局约 0.4 秒闪退，连崩 3 局，SIGBUS 都在 `s2a_nro_map`，地址都是 main+0xb958d0；同一个多款容器包里的另一款正常。

**根因**：这款 main 的一批导入由 romfs/nro/NmplDLL.nro 定义。起局时宿主（扮演 rtld）先把它们绑到报错桩，写入成功；游戏 DT_INIT 之后用 SetMemoryPermission 把 main 的 RELRO（导入表所在）改成只读，宿主照做 mprotect；随后游戏调 nn::ro 装这个 NRO，宿主补绑时直接往已只读的槽写 → SIGBUS。真机 rtld 对这类导入走延迟绑定，不受游戏设的页权限约束。

**做法**：补绑改经 `svc_mem.c s2a_loader_store64`：页可写直接写；游戏设成只读的数据页，经跟踪器同一钩子（guest_protect）临时加写、写入、恢复原保护；代码页一律不写（写不进就打红、留着报错桩，不崩进程）。iOS 上 W 块是 MAP_PRIVATE 读写映射、最大权限没压低，临时放开写是允许的。单测 `t_svc_mem`：走真实 SetMemoryPermission 设只读，直接写被信号杀（修前现场），装载器写入成功且写后仍只读。

## Metal 3 下计算派发的绑定会把共享编码器换掉

**现象**：时之笛 S2 在 macOS 15（#261，玩家 M4 Pro）上开场过场后 SIGSEGV，崩在 AGX ComputeContext `setBuffer`，栈 `m3_table_apply ← enc_c_dispatch ← dispatch`，崩前一行是「texture upgraded to allow format views」。Mac 上 `NXGAL_BE=mtl3` 稳定复现（第 10614 帧）。

**根因**：`dispatch` 先取共享计算编码器 `ce = dispatch_enc()`，再 `encode_args` 绑参数。绑图像 / 贴图视图要格式视图用途时会升级贴图（`tex_upgrade`），升级的拷贝走 `blit()`。Metal 3 拷贝要拷贝编码器，`blit_open_k` 会结束共享计算编码器 `g_blit`，本地 `ce` 成了已结束的编码器，接着派发就崩在驱动里。Metal 4 拷贝和派发同一个编码器，不换，所以只在 Metal 3（macOS 15 / iOS 18）出。绘制路径 11-02 已修过同一个坑（`draw` 绑定后检测 `g_enc != en` 重画）。

**做法**：`dispatch` 绑定后检测 `ce != g_blit` 就重派一次（贴图已升级，第二次绑定不再拷贝；深度护栏防死循环）。修后同局 11083 帧 0 崩溃，日志「dispatched again on a new encoder」。以后任何「拿到编码器后、用它之前」的步骤可能开拷贝的地方，都要按这个模式核一遍。

## 已装的内置引擎副本被改过，出包一直报「准备产物缺失或大小不符」

**现象**：#304，玩家 0.1.7 Mac 出包在「准备游戏程序」阶段失败，runtime_invalid，点名 `Binaries/S2ArmGame.app/Contents/Info.plist` 大小和清单对不上；重新打包也一样。

## 首写表的「槽号」其实是着色器内存储缓冲序号

**现象**：Splatoon Raiders（#41）对话后卡到一秒一帧。实局卡顿场景里每帧绘制笔数不变（约 1370 笔），GPU 时间却一路涨：91 → 565 ms（约 180 帧内）。

**根因**：一笔间接绘制（实例数由剔除计算着色器 `029d9c3ec1fcb39f` 用原子加写出）的实例数每帧本该清零，靠的是翻译器拿出来、由宿主在派发前代做的「首个线程写入」（first_store）。反射里 first_store 的 `reg` 是着色器内存储缓冲的序号（绑定项的 `index`），宿主却当 NVN 存储槽用（`S.ssbo[5][reg]`）。这个着色器 5 个存储缓冲 index 0..4 对应槽 4/2/0/1/3，清零写到了槽 0 的别的缓冲上，实例数每帧 +40 从不归零，那一笔越画越重。

**做法**：`nvn_refl.m` 解析 first_store 时按同一份绑定表把 index 换成该项的 `reg`（NVN 槽）。修在宿主，已出的包换新宿主即生效、不用重出。回放：实例数恒为 40，那一遍 127 ms → 1.5 ms，整帧 182 → 48 ms。单测 `t_nvn_first_store` ⑥：旧实现写进槽 0、槽 4 得 out[2] = 1。翻译器 Dsh.cs 的注释「reg = 存储缓冲槽，即 index」不成立（index ≠ 槽时），以后照宿主口径读。

## 改写器读 .eh_frame 不认绝对指针编码（absptr）

**现象**（#286，程序号 01E6A672A8800000，Windows 出包）：改写阶段 `s2a-rewrite` 退 1，`改写失败：不支持 EH 编码 0`。

**根因**：CIE 没写 R 增强时，FDE 的 pc_begin 按缺省编码 0（DW_EH_PE_absptr，AArch64 上 8 字节绝对地址）存；改写器只认 udata4 / sdata4 / udata8 / sdata8。位置无关映像里这个槽是装载器按 R_AARCH64_RELATIVE 填的：lld 缺省原位留 0、加数只在 RELA 表里，GNU ld 原位也写——只按 8 字节读原位会把 lld 产的函数全当成从 0 开始。

**做法**：`rd()` 认编码 0（8 字节）；绝对编码先查动态段 RELA 表（MOD0 + 4 → DT_RELA / DT_RELASZ）里同槽位的 R_AARCH64_RELATIVE 加数，没有用原位值。回归 `tests/rewrite_eh_absptr_test.py`：两个不相邻函数，期望函数范围 2 段——修前 absptr 两例退 1；只读原位不查 RELA 的半修法在 lld 例塌成 1 段。九款苹果金样逐字节不变。

## Apple C 改写器的暂存对覆盖叶子函数栈下区

**现象**：原创 AArch64 叶子函数在 `sp` 下保存值，经过一条 x18 改写点后从同一地址读回，得到跳板的暂存寄存器值。

**根因**：Apple ABI 给叶子函数保留 `sp` 以下 128 字节。`plain()` 在原 `sp - 16` 或 `sp - 112` 写入暂存寄存器对，和原指令的存活数据重叠。

**读数**（期望 → 实测）：Apple M1 Pro、macOS 14.8.5、基线 `2be4b3bef`，执行 7 个合成叶子函数。期望均读回 `0xbeef` → 修前 5 个重叠用例读回 `0x1234` 或 `0x5678`，2 个对照读回 `0xbeef`，修后 7/7 读回 `0xbeef`。同一测试换回基线改写器，5 个重叠用例再次失败。

**做法**：暂存帧移到原栈下区之外。需要读 `sp` 的指令用暂存寄存器取得原 `sp`，块尾恢复暂存寄存器并回放原写回量。

## runtime/src 里的苹果专用段用 `#ifndef __ANDROID__`，别用 `#ifdef __APPLE__`

**现象**：11-09 `quality/nro-relro-rebind`（5506137c2）合入后 main 全套红：钩子 android/gate.sh 的「端点核对」把 `svc_mem.c` 按 `-D__ANDROID__` 编，报 `info` / `VM_PROT_READ` 未声明 19 处。

## Switch 2 sdk 的服务客户端：要么整组在导入层接管，要么一个都不接

**现象**：11-09 #299 塞尔达无双封印战记（04003F40232DE000）iPad 一进 nnMain 就 SIGSEGV 地址 0（pc sdk+0x634024），5 局同点。

**根因**：nvn2.c 只在 main 导入层接管了 `nn::chat::Initialize`（回 0、不建对象）。真 Initialize 经 `detail::InitializeUserService` 建 chat:u 服务对象存进 sdk 全局 `g_UserService`，之后每个公开接口都「锁 → 取全局对象 → 读虚表」。对象没建，Initialize 后第一个 chat 接口就读空指针。原路径放不开：InitializeUserService 末尾要 `nn::chat::gsv::Initialize` + 5 次 `OpenVirtualDisplay`（GPU 服务，直连档没有，失败即 Abort），而 sdk 内部互调不经导入表、宿主接不住（loader.c 本模块有定义就绑自己）。

**做法**：main 导入层把 nn::chat 的 66 个公开接口整组接管为「没在聊」（RoomInfo 0xF0 字节全 0、Uid 全 0、模式 1 字节 0、缩放 1.0、设置照收、Attach*Event 挂永不触发的宿主事件）；格式取自 Raiders sdk 的客户端代理反汇编（公开接口 → 代理虚表 → 命令号 → 代理模板消息布局）。认不得的新名字打红行补表。教训：接管一个 sdk 服务的 Initialize 却不接管它的其余公开接口，等于埋空指针；审计「Initialize 回 0 是无服务分支」这类结论要先核其余接口靠不靠 Initialize 建的全局对象。

## Windows 版 metallib.exe 打不开含非 ASCII 字符的路径；全线编不过却当成功

**现象**（11-09 外部报告，Windows 11 中文版，用户名纯中文无空格，游戏库在 E:）：出库每支都报 `LLVM ERROR: Error opening 'C:\Users\<中文>\AppData\Local\S2A\j\<短号>\…'`，一支 metallib 都没出，进度条照走、退 0，最后出了一个没有着色器库的包。

## Windows Metal 目录选择在启动器里不生效（#137 合入后的实机验证）

**现象**（Windows 出包机，按启动器同一入口 S2Arm.exe + s2armctl 真实出包，盯进程表看 metal.exe / metallib.exe 从哪起）：`S2A_METAL_BIN` 指自定义安装、只把自定义安装加进 PATH、`S2A_METAL_BIN` 指不存在的目录，三种都出包成功，但起的全是 `C:\Program Files\Metal Developer Tools` 那份——自定义配置被悄悄忽略，负对照也没报缺件。

**根因**：#137 的 `metal_exe()` 本身对，但到不了它：随包 `s2arm_env.cmd` 把作业 PATH 换成只含随包工具（玩家 PATH 里的 Metal 目录看不见）；作业层 `core.env()` 剥掉所有 `S2A_*`，子进程拿不到 `S2A_METAL_BIN`。#137 的单测直接调函数，绕过了这两层。

**做法**：`s2arm_env.cmd` 换 PATH 前存进 `S2A_USER_PATH`；`metal_exe(environ)` 按「`S2A_METAL_BIN` → 玩家 PATH（`S2A_USER_PATH`）→ 官方默认目录」选；作业层在父进程选一次（`core.win_metal_dir`），显式写成子进程的 `S2A_METAL_BIN`，显式配置无效时原样传下去由预检报缺；预检的「环境缺件 metal」归 `metal_unavailable`。读数（期望 → 实际）：自定义 / 只设 PATH → 出包成功且进程全来自自定义安装；不存在的目录 → `【红】环境缺件 metal`、不起任何 Metal 进程。

## 服务层单测（JIT）绿、真机（NativeAOT）一跑就挂：Ryujinx 的反射泛型与 dynamic（11-09）

**现象**：金手指服务层单测全绿，真机上依次报「No parameterless constructor defined for OpMov`1[UInt32]」「CondGT`1[UInt32] is missing native code」「ArgumentNullException (key)」。

**根因**：iOS / Mac 包的 C# 是 NativeAOT 提前编译，只生成编译期见过的代码。Ryujinx 金手指编译器按宽度 `MakeGenericType` 再 `Activator.CreateInstance` 造操作（值类型泛型实例没人静态引用 = 没有机器码；`DynamicDependency` 只留元数据、不生成代码），运算全用 C# `dynamic`（运行时绑定，NativeAOT 不支持）。服务层单测跑在 JIT 上，这两类问题都测不到。

**做法**：值类型泛型实例在 `services/aot/rd.xml` 点名（`Dynamic="Required All"`），单测按反射核对名单；`dynamic` 换成按宽度的整数运算（compat 补丁 tamper-no-dynamic），单测扫源码防回退。以后接 Ryujinx 里没走过 AOT 的代码，先 grep `dynamic` / `MakeGenericType` / `Activator.CreateInstance`，并且必须上真机跑过才算验证。

## 打包贴图被当渲染目标画：建时没有 RenderTarget 用途

**现象**：11-09 #296 排查时开 Metal 调试层回放惊奇（010015100B514000），每帧 36 次「Texture at colorAttachment[0] has usage (0x01) which doesn't specify MTLTextureUsageRenderTarget」。主画面 4183（1920x1080）与 3 张 960x540 中间目标在宿主表里是 NvPkg（打包贴图）。

**根因**：tex_new 给打包贴图建 Metal 贴图时不带 RenderTarget（只有放宽存储 tex_widen 时才补），但游戏可以把同一段存储当渲染目标画。往没有 RenderTarget 用途的贴图里渲染是 Metal 的未定义行为。

**做法**：rp_begin_ex_ 开遍前，凡颜色附件缺 RenderTarget 用途（压缩格式与多重采样除外），先 tex_upgrade 就地补上（保留全部像素、换掉持有者的贴图），在关 blit 编码器之前做。注意：这不是 #296 黑块的根因（那是同遍自采样未隔离，见 #307），补了用途黑块照旧；它是另一个独立的未定义行为。

## NDK AMediaFormat 的 set* 没有返回值，COLOR_Format* 常量只在 Java 侧（issue #44）

**现象**：`s2a_mc.c` 按网上常见写法给 `AMediaFormat_setString/setInt32` 判返回值，NDK 29 真实头文件里这两个函数返回 `void`，编译报 `invalid argument type 'void' to unary expression`（android/codecs/s2a_mc.c，ctest-link 四个单库配置全红）。

**根因**：NDK 29 `media/NdkMediaFormat.h`：`AMediaFormat_setString/setInt32/setInt64/...` 一律 `void`，只有 `AMediaFormat_getInt32` 这类取值函数返回 `bool`；`AMediaFormat_new/delete` 才返回对象/状态。`CodecCapabilities` 的 `COLOR_Format*`（0x13/0x14/0x15/0x7F420888/0x7FA30C00）是 Java 侧常量，NDK 头不导出，ByteBuffer 模式的实际色彩要靠 `AMediaCodec_getOutputFormat` 的 `color-format`/`stride`/`slice-height`/`crop-*` 键读出来再分支。

**改法**：set 调用不判返回；输出端按读到的 color-format 分支（YUV420 planar 逐行拷贝、semiplanar/NV12 解交织进独立 U/V 平面），未知格式报契约失败而不是猜。`AMEDIACODEC_INFO_*`（TRY_AGAIN/FORMAT_CHANGED/BUFFERS_CHANGED）是 dequeue 的正常返回值不是错，要有界重试。

**读数**（期望 → 真结果，macOS 宿主 + NDK 29.0.14206865，ctest-link）：按 bool 判 set 返回 → 期望编过，真结果 `error: invalid argument type 'void' to unary expression`，4 个单库配置全红；改 void 语义后 → 期望全绿，真结果 242/242 链过、x86_64 -Werror 编过。

## MediaCodec color-format 0x7FA30C00 是 V 在前不是 NV12；FLEXIBLE 缺 stride/slice-height 键不能按半平面猜（issue #44）

**现象**：`s2a_mc.c` 把 `0x7FA30C00` 与 `0x7F420888`（COLOR_FormatYUV420Flexible）都并入半平面分支按 NV12（U 在偶数字节）解交织。评审核 AOSP `OMX_IVCommon.h`：`0x7FA30C00 = OMX_QCOM_COLOR_FormatYVU420SemiPlanar`，YVU = V 在偶数字节（NV21 排布），按 NV12 解会把 U/V 平面整体对调（红蓝反）。

**根因**：半平面存在两种字节序，color-format 常量决定哪个在先；FLEXIBLE 的语义是布局只能经 Image 平面 + pixelStride 查，ByteBuffer 模式不保证半平面——codec 没报 `stride`/`slice-height` 键时布局不可解释。

**改法**：0x7FA30C00 单走一支，`mc_split_uv` 的 U/V 目的指针对调；FLEXIBLE 只在 stride 与 slice-height 两键都报出且 size 够半平面需求时按半平面解，缺键报 UNSUPPORTED；失败 diag 带出 color-format/stride/slice-height 供真机按机型对照。

**读数**（期望 → 真结果，macOS 宿主 + hostmc 假 AMediaCodec）：夹具造 V 在前缓冲断言 U/V 平面内容 → 修前红在「yvu deinterleave: u/v not swapped」断言（非编译错）；对调目的指针后转绿；负控（去掉对调）回到同一断言红。FLEXIBLE 缺键用例期望 UNSUPPORTED → 修前真结果按默认 stride/宽解出帧（静默猜布局），修后 UNSUPPORTED。

## MediaCodec 隐藏帧（show_frame=0）不出图：「已入队未出图」计数会把活 codec 误判死（issue #44）

**现象**：判死界原用「已入队未出图 AU 数」上界 32。但 VP9 `show_frame=0` 的隐藏帧天然不出图（输入被正常消化），每个隐藏帧让计数 +1 永不回落；每 16 个 AU 藏 1 个隐藏帧的流，第 33 个隐藏帧（约第 528 个 AU，60fps 约 8.8 秒）触发 LIMIT 粘性失败——codec 其实是活的。宿主假 codec 还暴露出第二个模型错：假件把输入槽释放挂在「输出被消费」上，而真 MediaCodec 在 AU 被解码消化后即还输入槽，与出图解耦；隐藏帧照样还槽。

**根因**：把「排队未出图」当成 codec 死掉的信号。隐藏帧不是异常，输入缓冲归还也和出图无因果。

**改法**：判死界改为「连续零输出调用数」`empty_streak`：任何一次出图清零，连续 >32 才 LIMIT（stage=DEQUEUE）；输入槽饿死仍是独立界（真死 codec 不吃输入 → LIMIT@INPUT）。宿主假件输入槽改为每次 dequeue 消化一个排队 AU，`consume_inputs=0` 模拟真死 codec。

**读数**（期望 → 真结果，macOS 宿主 + hostmc 假 AMediaCodec）：pattern_mod=8 零星隐藏帧 300 AU 全程无失败、出 263 帧 → 修前（92aaeed in_flight 模型）真结果在第 33 个隐藏帧处 LIMIT 后粘性失败（3 断言红）；修后全绿。全静默流 33 连续无输出调用仍 LIMIT（边界不变）。
## NVDEC 重打包帧的压缩头是占位字节：硬件解不出 tx_mode / ref_mode / prev-MV 真实语义（issue #44）

**现象**：`McVp9Backend` 初版只比较「供给概率表 == 规范默认表」，没看 `Vp9NativeParams.TxMode / ReferenceMode / UsePrevFrameMvs`。评审探针：`TxMode=TX_MODE_SELECT、ReferenceMode=SELECT` 且供给表恰为默认的作业被判 `Decoded`——硬件照 1 字节占位压缩头解 tile，位流失步出花屏。

**根因**：`Vp9NativeHeader.Write` 末尾只写 1 个全零占位字节当压缩头（tx_mode、reference_mode、逐作业概率增量这些本由 vpx hook 带外注入）；`use_prev_frame_mvs` 位落在占位字节首位，恒 0。AMediaCodec 没有带外通道，照占位字节读：tx_mode=ONLY_4X4、reference_mode=SINGLE、无概率更新、prev-MV 不复用。判定只看概率表漏掉了前三类语义面（intra 帧规范本就强制 ONLY_4X4+SINGLE，不算违例）。

**读数**（期望 → 真结果，macOS 宿主 + managed_test 假 shim）：探针作业期望 NotRepresentable → 修前真结果 Decoded；补上三项判定（TxMode!=0 / ReferenceMode!=0 / UsePrevFrameMvs!=0 或 prevMvs 非空）后 NotRepresentable/NeedsKeyFrame；负控（去掉新判定）回到 `tx_mode_select not representable` 断言红。intra 作业 TxMode/ReferenceMode 字段任给仍 Decoded（规范强制，对照）。

**做法**：inter 作业三项语义超出占位语义一律回退；prev-MV 依赖回 NeedsKeyFrame（关键帧重置 MV 字段，依赖边只在那里闭合）；mvsOut/countsOut 硬件产不出就一概不写（客体缓冲保持上游真值，不写「全零」假值）。
